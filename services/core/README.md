# CPM Core — Go, первый рабочий dev-сервис

Core управляет организациями, подразделениями, учебными профилями, группами, школами, направлениями, расписанием, посещаемостью, отгулами и импортом пользователей. Код работает с локальной `cpm_dev`. Production и старый frontend не переключены.

**Telegram исключён:** нет бота, polling, настроек, чатов, выдачи паролей, Telegram API или соответствующего разрешения. `tg_name` остаётся обычным полем профиля для всех типов пользователей. Тесты, карточки, экзамены, домашние работы и расчёт/выдача рейтингов не входят в core.

## Что сейчас и что реализовано

В действующем коде эти функции находятся в Flask `cpm-back-main`, преимущественно в `cpm_back/blueprints` и `services/serv`. Отдельные профили студентов и сотрудников хранятся в MySQL; расписание — в MongoDB. Группа студента и проктора раньше была единственной общей связью. Организации и подразделения добавлены в новом dev-контуре.

| AS IS | Новый core |
|---|---|
| `students_bp`, `users_bp`: ученики, прокторы, экзаменаторы, супервизоры; создание, изменение, реквизиты, удаление | Список, поиск, карточка, создание профиля и аккаунта, редактирование, смена реквизитов, блокировка/активация; вместо физического удаления сохраняем историю |
| `groups_bp`: группы, состав, поиск, ученики без группы, назначение/снятие ученика и проктора | Группа принадлежит подразделению; один ученик имеет по одной группе в каждом участии; один проктор на группу и одна группа проктора в подразделении |
| `schools_bp`: справочник, активность, школа ученика | Справочник организации; изменение только её полным администратором; служебные заметки скрыты от обычных участников |
| `directions_bp`: только чтение направлений | Общий справочник организации; изменения полным администратором |
| `schedule_bp`: календарь в Mongo, школьная видимость, пересечения, пакетное сохранение | Такие же предметные поля и школьная видимость; отдельные подразделения, строгая валидация, атомарное добавление до 100 занятий |
| `class_days_bp`, `attendance_bp`: два механизма посещаемости | Один журнал core: день занятий подразделения, тип посещения, отметки и отчёт; старые таблицы не меняются |
| `zaps_bp`: отгулы, даты, изображения, решение, повтор/снятие привязки | Отгул в подразделении, собственные заявки ученика, обработка по праву `zaps.edit`, посещение типа 2, повтор и отвязка, защищённые вложения |
| `user_import_bp`: Excel, сессия предварительного просмотра, задания, отчёты | JSON/CSV/XLSX → сохранённый preview → атомарное подтверждение → отчёт; повтор подтверждения возвращает тот же результат |
| `admin_access_bp`: роли и сотрудники с фильтрованным доступом | Роли собственной организации, отдельная роль сотрудника в каждом подразделении; запрет повышения полномочий через обычное редактирование |
| Организационной области раньше не было | Текущая организация, создание/переименование подразделения, участие в нескольких подразделениях, доступный список, аудит изменений |

Это новый `/v1/core` контракт. Он не является заменой старого `/api` без изменений BFF/frontend. Механизм импорта не воспроизводит старый Excel-шаблон с автоматическим сопоставлением школ: используется явно описанный формат ниже. Preview можно заменить новой загрузкой; изменение отдельных строк существующего preview и отдельный фоновый import-worker пока не реализованы.

## Авторизация и доступ к объектам

Каждый бизнес-метод вызывает `POST /v1/auth/introspect` с исходным Bearer-токеном. Auth проверяет подпись, срок, сессию, версии аккаунта, актуальное участие и права. Core не принимает пользователя, роль или организацию из `X-User-*`, `X-Role`, тела или query. Отсутствующий/отозванный токен — `401`; недоступность auth — `503`, без разрешения операции. Кэш разрешений не используется.

Организация берётся из проверенного контекста. Каждый объект запрашивается с ограничением по организации и подразделению. Чужой ID не позволяет прочитать или изменить объект, обычно возвращается `404`. Неадминистратор работает только в выбранном подразделении, даже если у него есть другое участие. Для переключения нужно получить новый токен через `/v1/auth/context`. Полный администратор может обращаться к подразделениям своей организации без отдельного переключения.

| Кто | Доступ |
|---|---|
| Полный `admin` | Все операции в своей организации. Создание организаций и первоначального полного администратора остаётся ручным через БД; публичного платформенного администратора нет |
| `staff_admin` | Только `view/edit` соответствующего раздела в текущем подразделении. `edit` требует `view`. Для импорта нужны одновременно `upload` и `users`; для назначения группы — `groups.edit` |
| Студент | Собственный профиль, собственная группа без списка других учеников, направления, справочник школ, доступное расписание, свои посещения и отгулы. Создаёт заявку только за себя |
| Проктор | Собственный профиль и ученики назначенной группы; чтение и ручные отметки посещения только для этой группы; справочники и расписание |
| Супервизор | Собственный профиль, справочники, расписание и просмотр журнала своего подразделения |
| Экзаменатор | Собственный профиль, справочники и расписание; права на экзамены проверит будущий exams-сервис |

Разделы управления core: `users`, `groups`, `schedule`, `attendance`, `zaps`, `upload`. Роли также могут содержать разделы тестов/экзаменов/ДЗ/рейтингов. `telegram-bot` не поддерживается. Школы и направления общие для организации, поэтому их изменение доступно только полному администратору, а не сотруднику одного подразделения. Прежний флаг `directions.edit` делегированной роли больше не разрешает изменение общего справочника.

Создание сотрудника любого типа, назначение административных ролей, изменение реквизитов и блокировка аккаунта доступны только полному администратору. Делегированный `users.edit` позволяет создавать студентов и редактировать разрешённые профили. Если студент участвует в нескольких подразделениях, делегированный сотрудник не меняет его общий профиль: нужен полный администратор организации владельца. Другие организации могут читать профиль участника в своей области, но не изменять глобальные реквизиты. Принадлежность профиля владельцу хранится в `core_user_owners`.

Новые участия добавляются существующему пользователю своей организации. Добавление существующего глобального аккаунта в другую организацию пока выполняется вручную в dev БД; приглашения и подтверждение пользователем — следующий контракт, не обход проверки принадлежности по ID.

## История и ограничения удаления

Блокировка аккаунта сохраняет профиль, участия и учебную историю. Смена пароля/логина и блокировка увеличивают `auth_version`; предыдущие access/refresh-токены становятся недействующими. Для сотрудника обновляется также совместимая `session_version`.

Архивирование группы снимает назначение группы, но сохраняет участия и посещаемость. Из подразделения нельзя удалить последнее участие пользователя, собственное участие администратора операции, участие с историей посещаемости/отгулов и участие ученика с рейтингом. Пустое подразделение можно архивировать; подразделение с участниками — нельзя. День занятий с отметками нельзя удалить или перенести на другую дату; комментарий редактируется.

Проверка рейтинга сейчас читает существующий `Allratings` и постоянный признак `core_rating_locks`. Прежний `Allratings` не содержит подразделения, поэтому наличие записи консервативно запрещает снятие любых участий этого ученика. Core не рассчитывает рейтинг.

Будущий ratings-сервис **до сохранения первого рейтинга** обязан вызвать `POST /internal/core/rating-locks` с `X-Service-Key` и `{ "account_id": 123, "division_id": 456 }` и получить успешный ответ. Этот вызов идемпотентен, проверяет ученика и существующее участие. Удаляющего API нет. Снятие участия и установка признака блокируют строку аккаунта в транзакции, исключая гонку между этими операциями. Интеграция будущего ratings-сервиса обязательна; наличие произвольного документа в Mongo само по себе сейчас не создаёт признак.

Изображения отгулов: до трёх JPEG/PNG по 1 MiB, проверяется фактический формат, выдача отдельным защищённым методом. При одобрении дата связывается с днём своего подразделения; если дня нет, сохраняется `no_class_day` и доступен повтор. Отвязка или отклонение удаляет только отметки этой заявки. Одобрение, как в прежней логике, заменяет ручную отметку типом 2; прежнее ручное значение не восстанавливается при отклонении.

## Хранение и граница с auth

Стек: Go 1.27.1, `net/http`, MySQL driver, Excelize для XLSX. В контейнере нет Python. Новые предметные таблицы — `core_*`; `organizations`, `divisions` и организационные роли уже используются auth. Прежние 79 таблиц и девять Mongo-коллекций остаются со своей исходной структурой.

Для первого dev-этапа core создаёт профиль, аккаунт и проекции доступа **одной транзакцией в общей MySQL**. Хеш пароля получает от доверенного `POST /internal/auth/password-hash`: endpoint auth требует отдельный служебный секрет, не доступен по обычному пользовательскому токену. Формат совместим с текущим Werkzeug PBKDF2 SHA-256, 600000 итераций, случайная соль. Открытые пароли не сохраняются, не журналируются и не выдаются в GET. Пароль для создаваемого аккаунта задаёт администратор/файл импорта.

Это временная зависимость от схемы auth: core записывает `auth_users`, `auth_account_state`, проекции участия и ролей. Перед самостоятельным production-развёртыванием нужно вынести команды управления учётными записями в административный API auth и согласовать сохранение/повторы через outbox. Сейчас отдельный admin API auth и outbox не реализованы; нельзя считать сервисы полностью независимыми по данным.

Расписание нового core хранится в `core_lessons` MySQL, чтобы проверка принадлежности школы/подразделения, пересечений и пакетная запись выполнялись одной транзакцией. Прежняя Mongo `schedule` не изменяется и не мигрируется. Перенос календаря production — отдельный будущий этап. Справочники школ/профилей пока используют прежние таблицы и их ограничения, включая общую уникальность названия школы.

## API и DTO

[OpenAPI](http://127.0.0.1:8003/openapi.json) содержит все 68 публичных бизнес-методов и схемы входных DTO. Ответ бизнес-метода: `{ "status": true, "data": ... }`; ошибка: `{ "status": false, "error": "..." }`. Методы PUT заменяют указанный набор полей DTO целиком. Идентификаторы пользователей в URL и `account_id` — ID `auth_users`, а не совпадающие числовые ID профилей разных типов. `profile_id` возвращается отдельно.

- `/v1/core/me`, `/organization`, `/organization/users`, `/divisions`, `/roles`, `/schools`, `/attendance-types`, `/audit`.
- `GET/PUT /v1/core/organization/test-settings` — настройка пересчёта баллов при изменении теста.
- `/v1/core/divisions/{division}/users`, `users/{account_id}`, `users/{account_id}/credentials`, `users/{account_id}/active`.
- `/v1/core/divisions/{division}/memberships/{account_id}`.
- `/v1/core/divisions/{division}/groups`, `groups/{group_id}/members`, `/directions`.
- `/v1/core/directions`, `/directions/{direction}` — общий справочник своей организации; изменения только полным администратором. Старые URL подразделений сохранены и возвращают тот же общий список.
- `/v1/core/divisions/{division}/schedule`, `/schedule/bulk`.
- `/v1/core/divisions/{division}/class-days`, `class-days/{day}/attendance`, `/attendance-report`.
- `/v1/core/divisions/{division}/zaps` и методы заявок, изображений и дат.
- `/v1/core/divisions/{division}/imports` и `imports/{id}/commit`.

Пагинация списков: `limit` 1–200 (по умолчанию 100), `offset` 0–100000. Пользователи: `q`, `role`, `unassigned=true`. Группы/школы: `q`. Расписание, дни и журнал: обязательные `date_from/date_to` YYYY-MM-DD, до 366 дней; журнал поддерживает `account_id`. Отгулы: `status=set|apr|dec`. Для отчёта действует верхняя граница 1000 студентов / 10000 отметок; дальнейшая пагинация большого годового отчёта требует отдельного контракта.

JSON проверяется по типам, неизвестные поля и лишний JSON отклоняются. Проверяются длины, положительные ID, даты и время, существование и область всех ссылок. Пароль при создании/смене: 8–1024 байт. Тело запроса до 8 MiB. Нет rate limit или ограничения числа успешных входов: будущий ingress/BFF отвечает за него.

## Импорт

JSON: `{ "users": [ { "role": "student", "full_name": "DEV Иван Иванов", "class": 10, "tg_name": "dev_ivan", "login": "dev_ivan", "password": "example-password" } ] }`.

CSV/XLSX отправляется `multipart/form-data`, поле `file`. Первый лист XLSX, первая строка — заголовки. Обязательные колонки: `full_name`, `login`, `password`. Дополнительные: `role`, `class`, `tg_name`, `school_id`, `group_id`, `role_id`. По умолчанию `role=student`; для ученика нужен `class`. От 1 до 100 строк. `organization_id`/`division_id` в файле запрещены: область берётся из контекста и URL.

Preview проверяет все строки, принадлежность ссылок, допустимый тип пользователя, дубликаты логинов и права. Пароли сразу заменяются хешами auth. GET preview не выдаёт ни паролей, ни хешей. При commit проверки повторяются по актуальным данным, весь пакет сохраняется транзакцией; конфликт одной строки отменяет весь пакет. Commit выполняется синхронно; результат сохраняется и возвращается при повторе без повторного создания пользователей.

## Запуск и проверки

Из корня проекта, после подготовки dev MySQL и auth:

```sh
./dev/dev core-up
./dev/dev status
./dev/.venv/bin/python services/core/scripts/http_test.py
./dev/.venv/bin/python services/core/scripts/test_settings_http_test.py
(cd services/core && go test -race ./... && go vet ./...)
(cd services/auth && go test -race ./... && go vet ./...)
./dev/.venv/bin/python services/auth/scripts/http_test.py
./dev/.venv/bin/python dev/scripts/verify.py
```

Core доступен только локально: `http://127.0.0.1:8003`, auth — `8002`. Новые учётные данные окружения остаются в игнорируемых `dev/.env` и `dev/local/core.env` с правами 0600. Контейнер core: непривилегированный пользователь, файловая система только для чтения, tmpfs для XLSX, память до 512 MiB, ограниченные логи, healthchecks MySQL и auth, graceful shutdown.

Синтетические данные: текущие dev-пользователи, две организации, четыре подразделения, группы основного/резервного/математического контекста. `dev_core_staff` — один сотрудник: просмотр в основном подразделении и редактирование в резерве. Пароль — общий dev-пароль из `dev/local/accounts.json`, он не копируется в документацию.

HTTP-тесты проверяют все защищённые методы без токена, ограничения организации/подразделения/группы, запрет поддельных заголовков и повышения полномочий, актуальные права, отзыв токена, смену реквизитов, блокировку, все типы аккаунтов, CRUD, школьную видимость, транзакции расписания, посещение и отгулы, защищённые изображения, запрет удаления участия с рейтингом, JSON/CSV/XLSX, повтор commit. Созданные тестом предметные записи удаляются только из фиксированной локальной dev БД. Аудит сохраняется. Отчёт — `dev/local/core-http-report.json` без токенов и паролей.

Следующие интеграции: BFF/frontend, административный API auth вместо общей записи, приглашения между организациями, ratings → постоянный признак истории и события изменения core для остальных сервисов. Production-миграции, GitHub deploy и нагрузочное тестирование всего комплекса здесь не выполнялись.

## Core в локальном BFF и независимые отчёты

В режиме `NEXT_PUBLIC_CPM_BFF_DEV=1` BFF подключает существующие справочники школ, профили/аккаунты, участие и группы, а также новые read-only методы `GET /v1/core/divisions/{division}/dashboard`, `/students`, `/reports/tests`, `/reports/exams`, `/reports/attendance`. Production-ветки React сохранены. Добавление этих методов не расширяет доступ BFF к записям расписания, посещаемости, отгулов, сканирования, общих импортов или Telegram.

`dashboard` возвращает выбранное подразделение, роль, доступные разделы и nullable-счётчики `students`, `staff`, `groups`, `schools`. Недоступный счётчик равен `null`. У проктора ученики и число групп ограничены его текущим назначением в активной группе этого подразделения. `/students` использует существующий список профилей, принудительно выбирая `role=student`; назначение проктора дополнительно проверяется по актуальной связи Core. Списки пользователей/учеников, групп и состава группы имеют `limit` (1–200, по умолчанию 100), `offset` и поиск `q`. Состав группы больше не обрезается отдельным `LIMIT 1000`.

Отчёты принимают только `date_from` и `date_to` в ISO-формате, до 366 календарных дней. Контекст организации и подразделения берётся из живой проверки Auth; полный администратор либо супервизор читает отчёты выбранного подразделения. Делегированному сотруднику нужны соответственно `test-results.view`, `exams.view` или `attendance.view`; право `ratings.view` само по себе отчёты источников не открывает. Старый ключ `test_results` используется только при отсутствии канонического `test-results`; явный запрет канонического ключа не переопределяется старым разрешением. Dashboard сохраняет прежнее имя capability `test_results`, но проверяет её по тому же правилу. Ответ содержит текущий список учеников с отдельными `account_id`/`profile_id`, столбцы работ/дней, ячейки результатов, время чтения и явные ограничения источника. Логины, пароли, ответы тестов, вопросы и голосования экзаменов в DTO отчёта не входят.

Тесты читаются из существующего внутреннего снимка нового tests owner: опубликованные активные тесты по дате начала в Москве и официально принятые работы. Незавершённая попытка до отправки в этот контракт не входит; старая внешняя система тестов не подключена. `ready` с баллом `0` остаётся нулём; `queued`, `processing`, `retrying`, `failed` имеют `score:null`, даже если источник содержит старый балл. Экзамены читаются из актуального снимка exams owner и используют его действующий завершённый результат, включая пересдачу с худшей оценкой и решения по апелляциям. Классические и экзамены вне системы включены; отсутствующий результат остаётся `null`, имя экзамена сохраняется.

Посещаемость читается из нового attendance owner через его публичный отчёт с исходным Bearer-токеном: владелец повторно проверяет права. Старые `core_class_days`/`core_attendance` не служат источником нового `/reports/attendance`; прежний Core `/attendance-report` сохранён как отдельный совместимый контракт. Отсутствие отметки означает «не отмечено», а не отсутствие ученика.

Адреса источников задаются опционально `CORE_REPORTS_TESTS_URL`, `CORE_REPORTS_EXAMS_URL`, `CORE_REPORTS_ATTENDANCE_URL`. Без подключённого источника возвращается `503 <source>_reports_not_connected`; сбой, ошибочная область или неполные данные также закрывают отчёт с `503`, а не создают пустые результаты. Допустимы только фиксированные локальные адреса соответствующих сервисов, HTTP-переходы запрещены. Таймаут источника 8 секунд, ответ до 32 MiB, до 2000 учеников и 100000 ячеек. Снимок каждого владельца согласован внутри его сервиса; распределённая атомарность между Core и другим владельцем не обещается. Старые данные автоматически не мигрируют.

Read-only интеграционный запуск после согласованной сборки Dev: `./dev/.venv/bin/python services/core/scripts/bff_reports_test.py`. Он использует только существующие синтетические HTTP-данные из `dev/local/bff-ratings-demo.json`, не меняет предметные записи и сохраняет несекретный отчёт в `dev/local/bff-core-reports-http-report.json`.

## Пересчёт тестов по организации

`GET /v1/core/organization/test-settings` доступен авторизованному участнику и возвращает `{ "status": true, "data": { "organization_id": 1001, "recalculate_on_test_change": true, "revision": 0 } }`. Организация определяется по токену. Значение по умолчанию `true` сохраняет прежнюю автоматическую обработку изменений, требующих пересчёта; без созданной строки версия настройки равна `0`.

Полный администратор организации меняет значение через `PUT /v1/core/organization/test-settings` с `{ "expected_revision": 0, "recalculate_on_test_change": false }`. Оба поля обязательны, `false` явно поддерживается. Делегированный администратор подразделения не изменяет общую настройку даже с `tests.edit`. Успешное изменение возвращает новое значение и увеличенную версию; устаревшая `expected_revision` даёт `409`. Повтор без изменения значения сохраняет версию. Значение, версия, автор изменения и запись аудита фиксируются одной MySQL-транзакцией. Параллельные изменения, включая первое изменение версии `0`, сериализуются блокировкой строки организации.

Tests получает тот же DTO через `GET /internal/core/organizations/{organization}/test-settings` с `X-Service-Key`. Неактивная или отсутствующая организация — `404`; служебный ключ обязателен. При сохранении редакторских изменений tests фиксирует значение и версию настройки в событии изменения. Переключение применяется к будущим сохранениям и не отменяет уже принятые задания пересчёта. Включение само по себе не создаёт ретроактивных заданий, выключение не отключает первоначальную оценку новой сдачи. Неподходящие по прежним правилам изменения теста по-прежнему не требуют пересчёта.

Настройка хранится в расширении `core_organization_test_settings`; миграция `003_organization_test_settings.sql` идемпотентна и применяется dev-скриптом. Проверка `test_settings_http_test.py` читает реальные строки и аудит SQL, проверяет защиту прав, изоляцию организаций, отсутствие записи при ошибках/повторах, служебный DTO и гонку версий. По окончании теста исходный флаг восстановлен, версия остаётся монотонной. Отчёт: `dev/local/core-test-settings-http-report.json`.

7 октября 2026 настройка проверена на работающем dev: 63 проверки HTTP и записей SQL, 287 проверок основного core API, Go race и vet. Исходный флаг пересчёта сохранён после проверки.

## Контекст организации для cards

`GET /internal/core/cards-context` требует `X-Service-Key` и текущий Bearer. Возвращает `{status:true,data:{organization_id,directions:[{id,name}]}}` для выбранной организации. Разрешён ученику либо сотруднику с явным `train`/`cards`/`training.view` (и полному admin). Доступные направления сейчас равны активному справочнику организации: индивидуальных назначений направлений в core нет. Параметры чужого account/organization/division не принимаются. Владение карточками и прогрессом остаётся в cards; [контракт и проверки](../cards/README.md).

## Снимок для рейтинга

`POST /internal/core/ratings/snapshot` требует `X-Service-Key` (`AUTH_INTERNAL_KEY`). Bearer пользователя не заменяет служебный ключ. Строгий вход: `{organization_id,division_id,date_from,date_to,as_of}`; даты YYYY-MM-DD, период до 366 календарных дней включительно, `as_of` — RFC3339 в UTC. Организация и подразделение должны быть активными и принадлежать друг другу.

Ответ `{status:true,data:{source:"core",organization_id,division_id,accounts,directions,input_hash}}`. Ученик содержит `account_id`, отдельный `profile_id`, `full_name`, `class`, nullable `group_id/group_name/school_id/school_name/school_short_name` и `is_active`. Участники — текущие ученики подразделения, включая заблокированные аккаунты для сохранения истории; максимум 2000. Школа выдаётся только из справочника запрошенной организации. Направления `{id,name}` включают архивные названия, нужные для исторических тестов, максимум 2000. Всё читается одной read-only repeatable-read транзакцией, списки упорядочены по ID. SHA256 определяется возвращённой областью и данными без времени захвата и самого хеша. Снимок не создаёт рейтинг и не устанавливает метки истории; ratings вызывает `rating-locks` отдельно до первого сохранения результата.

## Permanent attendance history guard

После разрешения пользователя 09.10.2026 добавлен `POST /internal/core/attendance/history-reservations`: только `X-Service-Key`, строгий DTO `{organization_id,division_id,account_id,operation_key}`. Проверяет активное участие ученика и сохраняет постоянный marker в собственной `core_attendance_history_reservations` (миграция `004`). Ответ выдаётся после commit; повтор области возвращает неизменный reservation_id. Снятие участия сериализуется теми же блокировками и возвращает `409 membership_has_history`. Нет release; отмена отметки или отгула сохраняет защиту.

Это признак защищённой истории, а не копия отметок/заявок: предметный владелец — attendance. Служебный метод не опубликован в BFF. `scripts/attendance_history_http_test.py`: 53 реальные проверки, 8 гонок guard/revoke. Отчёт — `dev/local/attendance-core-history-report.json`. [Полный контракт](../attendance/docs/core-history-guard-proposal.md).

`POST /internal/core/attendance/cell-targets` validates and reserves up to 100 unique active students atomically in one division. Service key only; optional proctor_account_id/group_id must be paired and match a live assignment. Set-based locking/queries; stable permanent history reservations, no release or migration. See Attendance `docs/journal-performance.md`.
