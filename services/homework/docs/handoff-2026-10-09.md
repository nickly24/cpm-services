# Homework / File-work: доработка после аудита 9 октября

Homework сохраняет владение типами и заданиями подразделения, загрузкой, сдачей,
проверкой, оценкой и удалением файлов. File-work обрабатывает PDF через RabbitMQ
и S3. У Uploads нет второго процесса загрузки домашних работ.

## Отчёт и класс ученика

`GET /v1/homework/divisions/{division}/report` принимает `date_from`, `date_to`,
`type_id`, `account_id`, `group_id`. Успешный ответ:

```json
{"status":true,"data":{"organization_id":1001,"division_id":1001,
 "assignments":[{"id":1,"name":"Задание","type_id":1,"type_name":"ОВ","deadline":"2026-10-09T00:00:00Z"}],
 "students":[{"account_id":1,"full_name":"Ученик","group_name":null,"class":10,
 "results":[{"assignment_id":1,"result":null}]}]}}
```

`class` имеет тип integer или null, берётся из `members[].class` внутреннего
Core `/internal/core/homework-references` в проверенной организации и подразделении.
Неизвестный класс не заменяется нулём. BFF/UI должен передать поле в таблицу
`/reports/old-ov` и прежний XLSX экспорт, включая фильтрацию по классу.
`type_name`, null результата и оценка 0 сохраняются отдельно.

Права отчёта остаются прежними: ученик видит себя и опубликованные задания,
проктор свою группу, supervisor и сотрудник с `assignments.view` разрешённое
подразделение; полный admin — только собственную организацию. Чужие type/group/
account ID возвращают 404, запрещённый ученику чужой account — 403.
Фильтр `assignment_id` отчётом не поддерживается. GET assignments также проверяет
принадлежность фильтра `type_id` подразделению.

## Лимиты для интерфейса

GET `settings` и `assignments/{id}/workspace` → `limits` возвращают текущую
политику подразделения из `application_settings`, ключ `homework.{division}.limits`.
PUT settings доступен только полному admin своей организации.

Публичный `job.limits` содержит снимок, принятый при создании загрузки:

```json
{"max_source_bytes":10485760,"max_output_bytes":10485760,
 "max_pages":35,"dpi":120,"jpeg_quality":75}
```

Поле присутствует в create/complete, GET jobs, active jobs и active_job workspace,
cancel/retry ответах. Если сохранённый снимок повреждён, поле null: текущие
настройки не подставляются вместо него. Изменение settings не меняет снимок
существующей загрузки и её повторов. До создания использовать workspace.limits;
для ошибок существующей загрузки использовать job.limits.

Ошибки `source_too_large`, `processed_too_large`, `too_many_pages` относятся
соответственно к исходному размеру, результату сжатия и числу страниц.
MiB = bytes / 1048576. Интерфейс не должен фиксировать 10 MB или 35 страниц в
сообщениях. Поле `max_bytes` create upload оставлено для совместимости.
Здесь приведены примерные значения, а не константы интерфейса.

## Мониторинг и readiness

GET `monitoring` требует `monitoring.view`. Счётчики jobs/outbox/delete и recent
jobs ограничены организацией и подразделением, указанные явно в ответе.
Состояния shared инфраструктуры не содержат аккаунтов, заданий, ключей объектов,
bucket, реквизитов или подписанных URL:

```json
{"rabbitmq":true,
 "worker":{"state":"ok","received_at":"2026-10-09T10:00:00Z",
 "observed_at":"2026-10-09T10:00:00Z","rabbitmq":true,"tools":true,
 "processing":false,"fresh_instances":1},
 "storage":{"state":"ok","checked_at":"2026-10-09T10:00:00Z"},
 "processing_ready":true}
```

`rabbitmq` — соединение Homework с брокером. Worker каждые 10 секунд передаёт
состояние через `POST /internal/homework/file-work/heartbeat` со своим
`HOMEWORK_SERVICE_KEY`; bearer пользователя и отдельный Core key не принимаются.
DTO v1: schema_version, instance_id UUID, observed_at UTC, rabbitmq, tools,
processing, storage:{state:ok|error|unknown,checked_at:UTC|null}.
Все булевы поля обязательны. Максимум 4096 байт, неизвестные поля запрещены.
Повтор/старое observed_at того же экземпляра возвращает 409 stale_heartbeat и
не продлевает свежесть. Сигнал старше 30 секунд и часы дальше +5 секунд отвергаются.
Время storage.checked_at не может быть позже observed_at; допуск времени не
накапливается между полями. Config требует разных обязательных worker/Core
ключей длиной не менее 32 байт. Старый fallback на AUTH_INTERNAL_KEY удалён.

Без первого сигнала state=unknown; после 30 секунд без свежего сигнала state=stale.
Неизвестные булевы компоненты возвращаются null. S3 проверяется реальным
Put/Get/Delete небольшого синтетического объекта в отдельном префиксе
`file-work-health/{instance UUID}/probe` каждые 30 секунд; бизнес-задание не
создаётся. Последний probe старше 60 секунд считается stale. Ошибка, unknown или
stale любого обязательного компонента не дают processing_ready=true.
Состояние одного свежего неисправного экземпляра не скрывается исправным.
Реестр heartbeat находится в памяти Homework; после restart состояние unknown
до следующего сигнала. Это состояние инфраструктуры, а не доказательство
успешного завершения конкретного PDF — завершение подтверждается owner job/file.

File-work `/healthz` проверяет живой процесс, `/readyz` — Rabbit, инструменты,
свежий storage probe и принятый owner heartbeat. Homework `/health/ready`
проверяет DB и сообщает broker отдельно; полную processing readiness читать
из monitoring. Новых переменных окружения или таблиц для heartbeat не требуется.

## Границы и совместная проверка

Организация берётся из Auth introspection, текущий division проверяется на
каждом запросе; полный admin не получает доступ к другой организации. Core
проверяет references scope. Student jobs — только собственный аккаунт и scope;
draft/progress не раскрываются сотрудникам. File URL выдаёт Homework по текущим
правам на submission. Внутренние claim/result сохраняют generation + claim token
и org/div fencing. Бизнесовые переходы и расчёт оценки не менялись.

OpenAPI owner v1.1.0 описывает Report, nullable class, JobLimits, Monitoring и
внутренний heartbeat. BFF и frontend меняет только их владелец.

Проверка исходников: Homework `go test -race ./...`, `go vet ./...`; File-work
`go test -race -p=2 ./...`, `go vet ./...`; корректный JSON и ссылки схем OpenAPI;
стандартные Docker сборки обоих сервисов прошли. Шесть pure regression tests
генератора проверяют отдельный ключ, сохранение при повторе и отказ при явно
заданном общем или коротком ключе.

В согласованном окне после 19:34 МСК Core уже отдавал class. Только Homework и
File-work пересозданы с финальными образами. В прежнем dev HOMEWORK_SERVICE_KEY
совпадал с AUTH_INTERNAL_KEY (значения не фиксировались). Теперь worker key
отдельный и устойчивый при повторном prepare; три private файла имеют mode0600.
Проверено: общая `.env`, Core/Auth/Ratings ключ и все прочие значения S3/Rabbit
overlay не изменились. Runtime worker/Homework ключи совпадают друг с другом и
отличаются от Core key. Генератор `dev/scripts/homework_env.py` обновлён в этой
узкой согласованной области; новый механизм Auth operation delegation не внедрялся.

`dev/local/homework-audit-report.json`: **PASS, 459 assertions, cleanup=true**.
Реальный путь signed POST → Rabbit → File-work QPDF/Ghostscript → S3 → Homework
DB → submit/review/grade/download прошёл с двухстраничным PDF. Все пять значений
job.limits сохранились после изменения текущей политики (2 страницы → 1), новая
загрузка получила новые настройки. Core class10 прошёл до owner report, запросы
чужих org/div/type/account/group/job/file ID отвергнуты; приватный draft скрыт;
смена контекста того же staff account и отзыв live прав прошли.

Отдельные credential проверки через действующий HTTP: worker key → ratings
snapshot401; Core key → heartbeat401; Core key → claim403 forbidden (сохранённый
прежний контракт claim/release); worker key + invalid heartbeat body400.
Мониторинг после реальной обработки: worker=ok, storage=ok, processing_ready=true;
File-work ready200 подтверждает свежий принятый heartbeat и реальный probe.
Настройки1001/1002 восстановлены успешными owner PUT после тестов, собственные
accounts/roles/groups/assignments удалены. Во время теста сервисы не
приостанавливались и не перезапускались. Ошибки, stale/replay и S3 probe failures
этого изменения проверялись unit/HTTP fixtures; новых live outages не делали.

Оставшаяся зависимость: BFF/UI владелец подключает nullable class в таблицу/XLSX,
accepted job limits в сообщения и отдельные состояния monitoring. Owner/Core
HTTP подтверждён; совместная UI проверка относится к его следующему окну.

Совместный read-only сценарий Uploads завершён: владелец Uploads подтвердил
регистрацию ссылки на существующий student job, точный повтор, metadata/receipt
и download409 `use_homework_submission_file_url`. Другой ученик в той же org/div,
admin и другая организация доступа не получили; административные jobs/events/
sessions не раскрывали приватную ссылку. Homework GET job проверял bearer;
Uploads не менял upload/complete/retry/cancel/submit/review и не писал S3.
Uploads удалил свой file/receipt/event и дополнительное собственное участие;
затем Homework выполнил cancel/delete и guarded cleanup своего временного
account/type/assignment/job, подтвердив отсутствие этих строк. Приватный handoff
удалён. Это проверка границы домашних работ; она не означает завершения всех
импортов Uploads или согласование нового Auth operation delegation.

Для текущего dev допускаются только синтетические fixtures и согласованное
окно пересборки собственных сервисов/Core. Rabbit/DB/S3 не останавливаются.
Production, миграция реальных файлов и нагрузка 450 учеников здесь не проверялись.
