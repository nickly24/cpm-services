# Локальная интеграция attendance → BFF → UI

Объём расширен пользователем 08.10.2026. Standalone attendance на 8013 подключён через Go BFF на 8001 к React UI на 3001. Подключение включается только `NEXT_PUBLIC_CPM_BFF_DEV=1`; старый production режим и данные не переключаются.

## Граница владельцев

| Данные / экран | Владелец в локальном UI |
|---|---|
| Расписание, календари, ресурсные ссылки занятий | attendance; core предоставляет read-only справочники |
| Журнал, дни занятий, версии типов, собственный QR, сканирование, отчёт руководителя | attendance |
| Отгулы, даты, решения, retry/unlink, защищённые приложения | attendance |
| Аккаунты, сессии, организации и права по подразделениям | auth / core |
| Домашние задания, тесты, экзамены, рейтинг, карточки | прежние самостоятельные владельцы |

BFF добавляет 38 публичных операций `/bff/attendance/*`, сохраняет live cookie/context проверки и передаёт исходные CAS/Idempotency-Key. Division в этих путях — явная область операции, доступ к ней проверяет attendance по актуальным правам; выбор календаря не переключает кабинет. Клиентский organization_id не принимается. Internal/service-key методы в браузер не открыты.

Защищённые PNG/JPEG BFF отдаёт авторизованным JSON `{status:true,data:{mime,data}}`; UI использует data URL только после проверенного запроса. Поэтому обычная загрузка `<img>` не обходит обязательный `X-CPM-Context`. Тело attendance допускает 3 MiB для трёх ограниченных base64 изображений.

## Поведение UI

Личное расписание ученика объединяет только привязанные подразделения выбранной организации, независимо от активного кабинета. Переключение в режим выбранных календарей показывает доступные опубликованные календари. Наложения разрешены: кластер раскрывается гармошкой, отдельные карточки сохраняют источник, время и часовой пояс.

Редактор занятий собирает create/update/delete в единый пакет. Ревизия фиксируется при открытии первого редактора; изменения не принимают новую ревизию незаметно после обновления списка. Настройка календаря сохраняет прежние visibility/timezone. Конфликт 409 требует обновить и заново проверить изменения; автоматического повтора с новой ревизией нет.

Журнал и отгулы имеют собственный выбор подразделения. Действия недоступны до загрузки актуальных данных. UI отображает исторические имя/смысл/цвет типа из записанной отметки. Архивация типа не удаляет прошлое; отсутствие отметки не считается отсутствием ученика. Проктор получает разрешённую группу, руководитель — чтение отчёта. QR подписан и ограничен организацией, подразделением, днём и сроком; старый QR из сырого profile ID в BFF режиме заменён переходом к выбору дня. Камера открывается только по действию пользователя и заполняет токен перед отдельным подтверждением отметки.

Класс, группа и школа приходят из scoped Core projection через Attendance. Фильтры сравнивают ID, неизвестные значения имеют отдельный вариант. XLSX содержит только видимые строки, полные/короткие школьные названия и organization/division IDs; историческое название типа берётся из Entry snapshot. В режиме сканирования таблица и XLSX содержат только фактически загруженный день; полный период остаётся в списке выбора. При сужении периода выбранный день заменяется первым доступным, QR согласован с этим днём.

Решение отгула можно исправлять между approved/rejected с пустым ответом. Лимиты сохранены: до60 дат, текст/ответ до5000 символов. Одобрение поверх ручной/QR отметки сохраняет Entry.ID и историю, связывая живую отметку с отгулом. Другой linked zap остаётся защищён409.

При неизвестном исходе UI сохраняет исходные ключ, тело и ревизию. Кнопка повтора отправляет именно эту команду. Успешный повтор завершает редактор; потеря обновления списка после успешной записи не создаёт новую команду. Редакторы, камера, передача вложений и неизвестные команды блокируют переключение контекста между вкладками через существующий Web Locks механизм.

## Проверки и команды

```sh
./dev/attendance check
(cd services/bff && "$HOME/.local/bin/go" test -race ./... && "$HOME/.local/bin/go" vet ./...)
python3 services/core/scripts/attendance_history_http_test.py
python3 services/bff/scripts/attendance_http_test.py
(cd cpm_front_new && npm test && npx tsc --noEmit)
./dev/bff build-ui
./dev/bff start-ui
node services/bff/scripts/attendance_browser_test.mjs
```

HTTP и browser проверки выполняются последовательно: они используют общую CAS revision организации и собственные DEV fixtures. `dev/local/accounts.json` содержит локальный пароль, он не копируется в исходники или отчёты. Browser script использует установленный Playwright и локальный Chrome; отчёты/скриншоты сохраняются в игнорируемом `dev/local/attendance-*`. Скрипт потери ответа действительно сначала завершает запрос в BFF/owner, затем скрывает ответ от UI; это проверка реального receipt, а не mock сохранения.

Go-тесты дополнительно используют настоящий dev MySQL и явно тестовые auth/core/guard для полного журнала, отгулов, изображений, snapshot, CAS и прав. Тестовые организации очищаются только из трёх собственных attendance таблиц. HTTP/BFF/browser работают с настоящими auth/core/MySQL и реализованным permanent guard; тестовый guard в этих проверках не используется.

## Защита истории и границы проверки

Постоянный history guard core реализован после разрешения 09.10.2026. Его собственная таблица блокирует снятие участия даже после удаления отметки/отвязки даты; attendance не пишет в таблицы core. [Контракт и реальные гонки](core-history-guard-proposal.md). Весь домен отгулов, включая заявки, решения, даты и изображения, находится в attendance.

Руководитель сохраняет существующий выбор периода отчёта: BFF → core report → актуальный attendance owner. Это read-only адаптация отчёта, а не второй владелец отметок. Журналы других ролей подключены напрямую через BFF attendance.

Физическая камера deferred пользователем до выкладки. Production импорт и cutover выполняются отдельно, без dual-write.

Свежий scoped audit и178 owner HTTP проверок после новых исправлений: [handoff09.10.2026](acceptance-handoff-2026-10-09.md). Общий UI/Core/BFF обновляет их единый владелец.
