# Сканирование постоянного QR ученика

Локальный кандидат от 19 октября 2026 для общего релиза 20 октября. Новых маршрутов, миграций и настроек окружения нет.

Сотрудник выбирает разрешённое подразделение и существующий день занятий. QR ученика содержит десятичный **ID профиля** (`students.id` прежнего Python-монолита, текущий `auth_users.ref_id` для role=student), а не системный `account_id`. В профиле и быстром меню ученика остаётся постоянный QR; номер профиля также показан рядом с ним.

## Запрос и проверки

Прежний `POST /v1/attendance/divisions/{division}/class-days/{day}/scan` принимает тот же envelope `{expected_revision,data:{qr:"700"}}` и `Idempotency-Key`. Ответ успешной записи — прежний `Result<Entry>`, Entry.account_id является системным идентификатором, отличным от сканированного номера.

1. Auth introspection и Core Division проверяют текущие права сотрудника и активность организации/подразделения.
2. День должен принадлежать указанному подразделению. Числовой QR — положительное целое без знака и ведущих нулей; внешние пробелы обрезаются.
3. Attendance вызывает существующий service-key Core `/internal/core/homework-references` с `{organization_id,division_id,profile_ids:[700]}`. Новое необязательное поле `profile_ids` нельзя смешивать с `account_ids`. Core ищет только активного student с участием в указанной организации и подразделении; возвращает profile_id и account_id раздельно. Полная выгрузка учеников и поиск по чужим подразделениям не используются. Неоднозначность/отсутствие — отказ.
4. Attendance повторно проверяет принадлежность целевой учётной записи и права на неё. Проктор может отмечать только ученика своей текущей группы с подтверждённым назначением в Core.
5. Используется активный тип выбранного подразделения с `scan_default=true`. Без него запись запрещена.
6. Любая существующая неудалённая отметка этого ученика за этот день, включая ручную и связанную с отгулом, даёт `409 attendance_already_recorded`. Запись, её тип и история не меняются. Отменённую отметку можно поставить заново; обычное ручное редактирование остаётся отдельной операцией.

Операция выполняется внутри существующей транзакции с блокировкой состояния организации и CAS revision. Два новых сканирования при одной revision: один победитель, второй получает revision_conflict; после перечитывания повтор получит attendance_already_recorded. Отклонённые попытки не создают audit/receipt и не вызывают history reservation. Повтор **той же уже выполненной команды с тем же UUID и телом** возвращает исходную квитанцию, без повторной записи; это восстановление транспорта, а не новое сканирование.

## Совместимость и ошибки

- Прежние `attendance-qr-v1.*` поддержаны с исходной проверкой подписи, срока, организации, подразделения и дня. Новый простой номер всегда трактуется как profile_id, без fallback к account_id.
- `404 student_not_in_division`: профиль недоступен в выбранном подразделении. Нельзя раскрывать его сведения из другого подразделения.
- `400 invalid_student_qr`: неподходящий формат постоянного QR.
- `409 attendance_already_recorded`: дубль; интерфейс показывает, что запись не изменена.
- `409 scan_default_type_required`: не настроен тип сканирования.
- `403 forbidden`: недостаточно прав, в том числе чужая группа проктора.
- `503 dependency_unavailable`: не подтверждены данные Core/Auth; никакой отметки по предположению.

## Интерфейс

Раздел сканирования показывает только подразделения с правом записи attendance/scan; для проктора — назначенные ему подразделения с группой. День выбирается явно. Камера работает непрерывно и сохраняет каждую распознанную отметку без отдельного подтверждения. Повторные кадры одного QR подавляются на 2 секунды; сервер остаётся источником решения о дубле. Пока идёт запись, считывание приостановлено, параллельные команды не отправляются. Поддержан ввод номера с клавиатуры/аппаратного сканера с Enter.

При открытой камере нельзя менять подразделение, месяц или день. Неизвестный исход команды блокирует следующие записи до штатной проверки/повтора той же команды. Автоматической новой отправки нет. Физическая камера требует браузерного разрешения и HTTPS либо localhost.

## Порядок будущего выпуска

Сначала Core с опциональным profile_ids, затем Attendance, затем frontend. Старый Core не принимает новое поле; ошибку нельзя обходить глобальным поиском или подстановкой account_id. Перед публикацией собрать объединённый релиз заново; локальные адаптеры и production-снимки не входят в поставку.
