# Внешние тесты: граница BFF и интерфейс

Изолированная часть интерфейса подготовлена под согласованный контракт Go tests. HTTP и браузерные сценарии требуют реализованного и поднятого внешнего домена Tests; наличие маршрутов в BFF не подтверждает, что владелец уже их обслуживает.

## Владельцы данных

Tests хранит внешний тест и подтверждённые результаты. Каждая запись относится к одной организации и одному подразделению. Внешние тесты не входят в общий банк внутренних тестов и не имеют подключений: запись для другого подразделения создаётся отдельно. Внешний тест не содержит вопросов, попыток CPM-LMS или операций запуска/тренировки.

Uploads владеет исходным файлом, общей import session, preview, workflow/job и доставкой команды commit в Tests. Общие экраны загрузок и их API этой частью не меняются. BFF интерфейса внешних тестов не предоставляет обходной import endpoint и не отправляет Excel в старый backend. Предметная проверка/подтверждение импортных результатов остаётся в Tests; служебный контракт фиксируется владельцами Tests/Uploads отдельно.

## Публичные маршруты

Все маршруты браузера `/bff/tests/...` пересылаются в `/v1/tests/divisions/{selected_division}/...`. Подразделение берётся из текущей BFF session. Сохраняются существующие Origin/header/context проверки, HttpOnly cookie, живая introspection и пользовательский Bearer к владельцу; service key не добавляется. `organization_id`, `division_id`, произвольный upstream URL и внутренние импортные команды недоступны из браузера.

| Метод | Хвост маршрута | Назначение |
|---|---|---|
| GET/POST | `external-tests` | Каталог / создание |
| GET/PUT/DELETE | `external-tests/{external}` | Запись / изменение / подтверждённое удаление |
| GET | `external-tests/{external}/delete-preview` | Количество результатов, ревизия теста, токен и срок подтверждения |
| GET | `external-tests/{external}/results` | Подтверждённые результаты по отдельным правам |
| GET | `external-tests/{external}/history` | История каталога и результатов |
| PUT/DELETE | `external-tests/{external}/results/{account}` | Административная коррекция результата |
| GET | `external-results` | Результаты с данными теста; student только себя, staff по разрешённой области |

Создание и коррекции сохраняют `Idempotency-Key` при неопределённом HTTP-ответе. Ключ отделён по текущему кабинету и содержимому команды. Коррекция передаёт захваченные `expected_revision` теста и `expected_result_revision` строки; удаление теста передаёт ревизию из показанного preview и его `confirmation_token`. После конфликта удаления нужно обновить подтверждение. Владелец проверяет права и область каждой команды.

`account_id` используется в API результатов, `student_id` означает ID профиля ученика. UI показывает оба идентификатора в административном workspace. Балл `0`, результат с `score:null` и отсутствие результата отображаются по-разному. Несовпадение организации/подразделения ответа с текущим кабинетом, а также чужая оценка в student self response завершаются ошибкой; пропавший источник не превращается в успешный пустой список.

## Экраны

- Административный каталог подразделения объединяет внутренние и внешние записи до поиска/фильтров/пагинации. Банк показывает внутренние тесты. Меню создания снова содержит «Вне системы».
- Workspace внешнего теста показывает дату, направление, результаты и историю; редактирование названия/направления/даты учитывает `can_edit` и захваченную ревизию. Catalog-only сотрудник видит карточку без баллов; результаты требуют отдельного разрешения. Минимальная ручная коррекция является новым дополнением к legacy: изменение/удаление существующей оценки и добавление по явно указанному ID аккаунта, только с `test-results.edit`. Пустое поле оценки сохраняет неизвестный балл, а не ноль.
- Раздел административных результатов учитывает учеников, у которых есть только внешние результаты. Для выбранного ученика внешние оценки отображаются отдельной таблицей, без попытки открыть их как внутренние сдачи.
- Ученический каталог показывает внешние тесты без кнопок сдачи, тренировки или просмотра ответов. Обзор включает внешние тесты с результатом, полный каталог — также без результата. «Успеваемость» читает собственные внешние результаты текущего подразделения.

- `components/admin/test-results/admin-external-results.tsx`.
- `components/student/performance/student-external-results.tsx`.

Точечные добавления к существующим файлам:

- BFF `internal/bff/tests.go`, `tests_test.go`: scoped allowlist и проверка проксирования.
- UI `lib/admin/admin-tests-api.ts`, `admin-tests-types.ts`: внешний create/delete adapter, действия и workspace view.
- `lib/bff/tests-admin.ts`, `tests-student.ts`: объединение внешнего источника; соответствующие прежние unit suites сохраняют изоляцию внутренних сценариев.
- `components/admin/tests/admin-tests-section.tsx`, `admin-create-test-menu.tsx`, `admin-test-card-actions.tsx`, `admin-external-test-delete-dialog.tsx`: входы в новые сценарии.
- `components/admin/test-results/admin-test-results-section.tsx`, `components/student/performance/student-performance-section.tsx`, `components/student/tests/test-detail-panel.tsx`, `lib/student/tests-api.ts`: внешние панели, корректная подпись неизвестного балла и отображение точного дробного балла нового API.

Auth cookie/context, attendance, общий upload screen/API и navigation не изменялись. Embedded OpenAPI нужно обновить с поднятого Tests после добавления владельцем маршрутов; текущий генератор уже преобразует division-scoped пути Tests в правильные browser пути.

## Проверки изолированной части

15 frontend unit checks внешнего контракта покрывают ноль/null/missing, область организации/подразделения, own-only результат, отдельные account/profile ID, idempotency, ревизии и preview, отмену запросов, страницы, недоступный источник, student merge и фильтры каталога/банка. Целевой ESLint новых файлов и TypeScript проходят. Полный frontend suite и Go BFF race/vet проходят на общем workspace; точные итоговые числа обновляются после очередного полного прогона.

Пока не подтверждены: реальные HTTP Tests→BFF, browser workflows и рейтинг с внешним источником. Эти проверки выполняются после реализации/поднятия домена Tests и согласованной пересборки BFF/UI. Изолированные unit checks не заменяют их.
