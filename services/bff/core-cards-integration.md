## Подключённый Core

8 октября 2026: локальный BFF (`8001`) подключает Core (`8003`), React использует новые ветки только при `NEXT_PUBLIC_CPM_BFF_DEV=1`. Production-ветки сохранены; перенос старых данных, production-конфигурация и deployment этим изменением не выполнялись.

В публичном встроенном OpenAPI доступны 31 операция Core:

| Публичный путь BFF | Операции и область |
|---|---|
| `/bff/core/me`, `/directions`, `/divisions` | GET собственного профиля и доступных справочников |
| `/bff/core/roles` | GET ролей своей организации, только полный администратор |
| `/bff/core/organization/test-settings` | GET; PUT общей настройки только полным администратором, с `expected_revision` |
| `/bff/core/schools`, `/schools/{school}` | GET справочника/карточки; POST/PUT общей школы только полным администратором |
| `/bff/core/users`, `/users/{user}` | GET списка/карточки, POST пользователя, PUT профиля в выбранном подразделении |
| `/bff/core/users/{user}/credentials`, `/active` | PUT реквизитов/активности, только полный администратор владельца аккаунта |
| `/bff/core/memberships/{user}` | PUT/DELETE участия с защитой истории и повышения полномочий |
| `/bff/core/groups`, `/groups/{group}` | GET/POST и PUT/DELETE группы выбранного подразделения |

| `/bff/core/attendance-report` | Сохранённый совместимый read-only контракт старого журнала Core |

Организация определяется живым Auth-контекстом. Для scoped-путей BFF подставляет текущее подразделение; передавать свою организацию/подразделение в query нельзя. Каждое чтение/изменение проходит авторизацию владельца. Предыдущая `X-CPM-Context` после переключения кабинета возвращает `409`. Cookie BFF остаётся HttpOnly/SameSite Strict, Bearer-токен не передаётся React.

## Школы, пользователи, группы и сводка

Школа — общий справочник организации. Обычные участники видят только активные школы; служебные заметки скрыты без права просмотра. Создать или изменить справочник может полный администратор. При назначении школы ученику Core проверяет принадлежность организации. Аккаунт (`account_id`) и профиль (`profile_id`) — разные ID; API и UI сохраняют это различие.

`users.view/edit` управляет просмотром/изменением профилей в подразделении. Делегированный сотрудник создаёт только студентов; создание сотрудников и назначение административных ролей остаются полному администратору. PUT профиля заменяет `full_name`, `class`, `tg_name`, `school_id`; смена группы выполняется отдельным методом. Изменение общего профиля, влияющее на другие подразделения, требует полного администратора. Реквизиты PUT требуют новый пароль: старый пароль/хеш не читаются. Создание аккаунта не имеет idempotency-контракта; после неизвестного исхода UI сверяет существующий аккаунт по введённому логину, не повторяя POST автоматически и не сохраняя пароль в журнале команды.

`groups.view/edit` действует отдельно от `users`. Архивирование группы и снятие назначения сохраняют участие/историю. Отзыв участия защищён от удаления участника с рейтингом/историей и последнего необходимого участия. Проктор читает учеников своей текущей активной группы: `/students` принудительно фильтрует `role=student` и проверяет актуальное назначение `core_proctor_groups` в выбранной организации/подразделении. При отсутствии группы или устаревшем назначении список пустой, а не общий список подразделения.

Пользователи, ученики, группы и состав группы используют `limit=1..200` (по умолчанию 100), `offset` и `q`. Состав группы больше не имеет отдельного молчаливого `LIMIT 1000`. UI полностью собирает нужные страницы; фильтры не должны работать только по первой странице. Сводка `/dashboard` возвращает выбранное подразделение, роль, `capabilities` и счётчики `students/staff/groups/schools`. Недоступное число — `null`; ноль означает реально пустую доступную область. Проктор получает число учеников/групп только своей группы. Счётчик школ относится к организации, остальные — к выбранному подразделению.

## Отдельные отчёты супервизора

Супервизорские страницы тестов, экзаменов и посещаемости в Dev читают новые `/bff/core/reports/*`. Они не зависят от ранее опубликованного рейтинга: Core читает актуальный результат у правильного владельца. Период задаётся `date_from/date_to`, ISO-даты, не более 366 календарных дней. Есть поиск ученика, фильтры группы/школы/класса/направления, горизонтальный скролл таблицы и Excel с сохранением числового нуля. При ошибке источника интерфейс показывает ошибку; ранее загруженный отчёт помечается как прежний и не выдаётся за обновлённый.

Читатели: полный администратор и супервизор выбранного подразделения. Делегированному сотруднику нужны `test-results.view`, `exams.view` или `attendance.view` соответственно. Исторический ключ `test_results` используется только при отсутствии канонического `test-results`; явный канонический запрет имеет приоритет. Только `ratings.view` не открывает независимые отчёты источников. Студент, проктор и экзаменатор без административного права не читают полный отчёт. Текущий состав учеников берётся из Core и ограничивает вывод результатов; результаты аккаунта без текущего участия не добавляются в отчёт.

Ответ содержит `source`, организацию/подразделение, период, `as_of`, учеников, столбцы, ячейки и `limitations`. Логины, пароли, Telegram-профили, ответы/вопросы тестов и экзаменационные голоса в отчёт не входят. Пределы: до 2000 учеников, 100000 ячеек, ответ источника до 32 MiB, HTTP-таймаут 8 секунд; HTTP-переходы запрещены. Снимок каждого владельца согласован внутри его сервиса; общая распределённая транзакция Core/источника не обещается.

| Отчёт | Актуальный владелец и семантика |
|---|---|
| Тесты | Новый tests: служебный `POST /internal/tests/ratings/snapshot` после живой проверки прав Core. Только опубликованные активные тесты по дате старта в Москве и официально принятые работы. `ready` с баллом `0` остаётся 0; `queued/processing/retrying/failed` имеют `score:null` и подпись состояния, даже если есть старый балл. Отсутствие работы — отдельное `missing/null`. До отправки попытка не входит в контракт. Старые external tests не подключены, ограничение явно указано. |
| Экзамены | Новый exams: служебный `GET /internal/exams/rating-snapshot` с фиксированной областью/периодом. Классические и `outside_lms`; имя владельца сохраняется, для старого контракта без имени есть fallback. Используется действующий завершённый результат владельца: худшая завершённая пересдача 0 заменяет прежний результат 4 после апелляции. Отсутствие результата — `missing/null`. Для вне системы выводится оценка 0–5, не исходные десятичные баллы. Метаданные попытки/апелляции сохранены. |
| Посещаемость | Новый attendance (`8013`): публичный `GET /v1/attendance/divisions/{division}/attendance-report` с исходным Bearer, владелец повторно проверяет права. `source_revision` сохраняется. `unmarked_is_absent=false`: отсутствие отметки отображается «Не отмечено», не превращается в отсутствие ученика. Старые `core_class_days/core_attendance` не используются в новом `/reports/attendance`. |

Источники опционально подключаются локальными `CORE_REPORTS_TESTS_URL`, `CORE_REPORTS_EXAMS_URL`, `CORE_REPORTS_ATTENDANCE_URL`; production-адреса по умолчанию не задаются. Без адреса соответствующий отчёт возвращает `503 <source>_reports_not_connected`. Сбой, неправильная область или неполные данные источника дают `503`, а не пустой отчёт/нулевые результаты. Источник тестов/экзаменов получает только внутренний ключ; attendance получает только Bearer пользователя — заголовки не смешиваются. Внутренние снимки не добавлены в BFF allowlist.

## Границы этой работы

Добавление Core/BFF/React не переносит Telegram, общий импорт, миграцию посещаемости/расписания/отгулов/сканирования и соответствующие экраны или записи. Уже существующие отдельные правки attendance/BFF/UI из соседней работы сохранены. Новый Core отчёт посещаемости лишь читает текущего владельца; старый совместимый Core `/attendance-report` остаётся отдельным контрактом. Старые данные, внешние legacy tests и production не объявляются полностью переключёнными.

## Карточки через новый BFF

Публичная граница `/bff/cards/*` содержит 19 разрешённых операций владельца `/v1/cards/*`: каталог администратора, дерево ученика, разделы направления и фильтры, ручные темы/карточки с CRUD, карточки опубликованного теста, партии обучения, настройки/прогресс, подготовка и подтверждение преобразования карточек в черновик теста. `imports/parse`, private/internal маршруты и произвольные владельцы не открыты. Общий Upload/import экран остаётся вне этого этапа. Подготовка экзамена продолжает работать через ранее подключённый exams; React объединяет реальные деревья cards и exams по направлению, не теряя ручные темы или тесты.

Карточки и прогресс принадлежат **организации**, не отдельному подразделению. Ручные карточки доступны по живым направлениям Core и `train.view/edit`; студент обучается без административного доступа. Прогресс и настройки ученика сохраняются при смене подразделения внутри организации; другая организация получает собственный каталог. Тестовые карточки дополнительно проверяет tests: ключи ответов доступны только в разрешённой ученику области после завершения теста/разрешённой сдачи и при `answers_visible`. Скрытые ответы не раскрываются даже через административный study URL; admin-каталог содержит лишь метаданные видимости и количества.

Ссылки ученика однозначны: `/train/manual/{numeric_id}`, `/train/test/{24hex}`; существующий экзаменационный маршрут сохранён. Имена разделов не используются как идентификатор. Поддерживаются `all/unlearned/learned/stale`, поиск, фильтр изученности, страницы разделов, партии 10/20/30 и восстановление позиции. Ответы single/multiple/text проецируются из актуальной версии теста. Изменение текста или ответа оставляет стабильный `card_ref`, меняет fingerprint и показывает «Ответ изменён»; старый fingerprint не отмечает новую версию изученной. Нулевое количество карточек остаётся нулём.

Правки темы/карточки используют owner `expected_revision`. React сохраняет UUID логической команды при потере ответа и предлагает проверить/повторить её; изменение формы до разрешения неизвестного результата заблокировано. Если после неизвестного результата доступ отозван, последующий 401/403/404 не стирает прежнюю команду: после восстановления прав повтор использует тот же UUID. Cards хранит приватную квитанцию и предметное изменение в одной SQL-транзакции существующего хранилища. Повтор с тем же UUID/входом возвращает исходный результат создания, изменения или удаления; другой вход с тем же UUID получает 409. Квитанции недоступны через публичные preview URL. Новая миграция таблиц для этого не нужна.

Преобразование создаёт снимок выбранных карточек с сохранением порядка и полного многострочного ответа, по 1 баллу на вопрос. Commit создаёт **редактируемый черновик**, а не опубликованный тест; повтор после потери ответа возвращает тот же `draft_id`. Preview принадлежит автору и исходному подразделению. Смена кабинета/выход удерживается общим Web Lock при открытом редакторе или неизвестном результате. Общий import и legacy внешние тесты не участвуют.

## Общая граница и проверка стенда

Core/Cards подключены к существующему режиму `NEXT_PUBLIC_CPM_BFF_DEV=1`. Owner URL фиксированы локальными настройками; selected division в Core берётся из актуальной auth-сессии, область Cards — из владельца. Токены/служебные ключи в браузер не передаются, BFF не пишет в БД и не повторяет бизнес-запросы автоматически. Смена кабинета делает прежний `context_revision` недействительным для обоих семейств; параметры подмены account/org/division и дубли фильтров отклоняются. Списки Core проходят страницы по 200 записей, включая состав группы в домашках. Ответы Core/Cards ограничены 64 MiB; входной JSON Cards — 10 MiB, Core — 1 MiB.

На локальном стенде пересобраны только Core8003, Cards8008 и BFF8001. Auth, tests, homework, calculate, Rabbit, экзамены8010 и отдельный экзаменационный Core8011 не перезапускались этим этапом. Новый Core настроен на текущие tests/exams/attendance источники. Существующие записи прежних проверок сохранены; новые Cards/Core UI фикстуры имеют отдельные DEV имена. Настоящая production-миграция записей не выполнялась.
