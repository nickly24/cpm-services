# Рейтинг через BFF и React UI

Локальная интеграция существующих `ratings` и `calculate` с `cpm_front_new`. Организация берётся из актуального auth-контекста, подразделение — из выбранного кабинета. Бизнес-правила и публикация остаются у владельцев сервисов.

## Контракт браузера

| BFF | Владелец / назначение |
| --- | --- |
| `POST /bff/ratings/jobs` | `/v1/ratings/divisions/{session.division_id}/jobs`, период и `Idempotency-Key` |
| `GET /bff/ratings/jobs`, `jobs/{UUID}` | История и прогресс выбранного подразделения |
| `POST /bff/ratings/jobs/{UUID}/cancel`, `retry` | Отмена / новая ревизия; retry требует нового ключа |
| `GET /bff/ratings/ratings` | Опубликованные строки, `q`, `limit`, `offset`, `version` |
| `GET /bff/ratings/me` | Только собственная строка ученика |
| `GET /bff/ratings/accounts/{account_id}` | Детали разрешённого ученика |
| `GET /bff/ratings/versions` | Только завершённые публикации подразделения |
| `GET /bff/ratings/report` | Полный разрешённый JSON-отчёт; XLSX формируется клиентом |

Всего десять публичных операций. В embedded OpenAPI схемы имеют префикс `Ratings_`. Internal snapshots, персональные входы calculate и callbacks не доступны через BFF. Bearer и service key в браузер не передаются. Cookie, Origin, свежий auth/me и `X-CPM-Context` проверяются общей границей BFF; смена кабинета отклоняет предыдущие запросы. Параметры подмены организации/подразделения и произвольного upstream запрещены. `status_url` создания задачи переписывается на публичный BFF URL.

## Расчёт и источники

`ratings` снимает согласованные по хешам данные core, homework, tests и exams, сохраняет персональные входы, отправляет outbox через RabbitMQ и принимает результаты calculate. Публикация всего подразделения происходит атомарно: неполный staging не попадает в таблицу, отменённая или старая ревизия не заменяет новую. Ранее опубликованные данные остаются доступны во время пересчёта и при отказе источника.

Алгоритм `legacy-rating-v1`: `H × 0.25 + E × 6 + T × 0.45`. Домашние работы — только точный тип «ОВ», дедлайн включён в период и предшествует текущему московскому календарному дню; сданный ноль является результатом, не сданная работа входит в знаменатель с нулём. Повторный штраф UI не применяет. Экзамены имеют равный вес, учитывают эффективную завершённую попытку, апелляцию и более низкую пересдачу. Баллы внешнего экзамена не заменяют оценку. Тесты сначала усредняются по направлениям, затем между направлениями; queued/processing/retrying/failed и ready без результата блокируют публикацию.

Один account в двух подразделениях имеет независимые источники, задачи, место и публикации. UI сохраняет `place`, рассчитанный владельцем по всему опубликованному подразделению, до фильтрации и пагинации. Детали используют `account_id`, отдельно от профильного ID. Нули, отсутствующие результаты, отсутствие первой публикации и неактуальная публикация отображаются раздельно.

## Роли и интерфейс

Администратор и сотрудник с `ratings.view` читают рейтинг, версии, задачи и отчёт. Запуск, отмена и повтор требуют также `ratings.edit`; окончательное разрешение проверяет owner. Руководитель читает публикации и ход расчёта без команд изменения. Ученик получает только свой результат. Проктор получает только учеников своей текущей группы, без административных задач и полного отчёта. Переключатель верхней панели выбирает разрешённый auth-контекст и сбрасывает старое состояние UI.

Длительный расчёт отслеживается чтением задачи; accepted ответ не является готовым результатом. Повтор передачи команды с неизвестным исходом использует прежний UUID Idempotency-Key и тот же период. История версий содержит только завершённые публикации. Сведения об актуальности возвращает ratings; UI не вычисляет собственную формулу и не заменяет недоступный источник нулём.

## Граница полноты

Dev подключён к реальному Go exams на 8010, `exams_mode=required`. Внешние тесты из legacy MySQL ещё не перенесены владельцем tests: текущий dev явно использует `external_tests_mode=dev_internal_only`. Эта интеграция подтверждает внутренние тесты и обе модели экзаменов. Режим `required` для внешних тестов блокирует расчёт до появления явного массива `external_tests` у источника. Неперенесённые legacy данные не выдаются за проверенный нулевой результат.

## Повторная проверка

При работающих dev auth/core/homework/tests/exams/ratings/calculate, DB и Rabbit:

```sh
docker compose -f dev/compose.bff.yaml up -d --build
./dev/bff ui
dev/.venv/bin/python services/ratings/scripts/bff_integration_test.py
# Dev UI, основной административный сценарий содержит только собственные same-period jobs:
node services/bff/scripts/ratings_browser_admin.mjs --published
node services/bff/scripts/ratings_browser_roles.mjs
# После создания fixtures и после финальной пересборки:
dev/.venv/bin/python services/bff/scripts/ratings_http_smoke.py
node services/bff/scripts/ratings_browser_roles.mjs --read-only
node services/bff/scripts/ratings_browser_smoke.mjs
```

Fixtures создаются через публичные API в отдельных синтетических подразделениях. Manifest `dev/local/bff-ratings-demo.json` и отчёты остаются в игнорируемом local-каталоге. Пароли и токены не включаются в несекретные отчёты. Повторная read-only проверка не изменяет бизнес-данные.
