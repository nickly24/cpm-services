# Tests

Синтетические файлы для импорта JSON/OnlineTestPad и внешних результатов XLSX
скачиваются защищёнными native GET методами; схемы и sample предметного DTO
доступны отдельно. Контракт маршрутов, MIME, прав и форматов:
[import-templates-contract.md](docs/import-templates-contract.md).

Фоновые импорты после явного подтверждения пользователя: source-кандидат
Rev2 с direct Auth, readonly prepare и receipt-only. Контракт, настройка и
границы проверки: [background-import-contract.md](docs/background-import-contract.md).

Go-сервис на порту `8004`: банк тестов, подключения к подразделениям, независимые копии, вопросы, неизменяемые версии, история редактора, черновики и сдача в выбранном подразделении. Официальная сдача сохраняется сразу и возвращает `202`; сообщение передаётся через долговечный outbox. Calculate асинхронно выставляет баллы официальных сдач и пересчитывает их при значимых изменениях теста с учётом настройки организации. Тренировочный вопрос проверяется отдельным синхронным методом calculate.

## Модель и права

Один тест принадлежит одной организации и одному подразделению-владельцу. Направление одно для всего теста, из общего справочника организации в core. Подключения возможны только к подразделениям той же организации. Название, описание, направление и вопросы общие; опубликованность, окно доступности, время прохождения, проходной процент и просмотр ответов задаются отдельно для каждого подключения.

Попытка и сдача сохраняют конкретные `organization_id`, `division_id`, `account_id`, `test_id`. Подразделение фиксируется при старте. Списки тестов, попыток, сдач и статистика отбирают выбранное подразделение до подсчёта `total` и пагинации. Официальная активная попытка уникальна по организации, подразделению, аккаунту и тесту; принятая сдача сохраняет эту уникальность до административного сброса. Независимая копия имеет другой ID теста.

Общее содержимое меняет редактор подразделения-владельца либо полный администратор организации. Редактор подключённого подразделения управляет его настройками. Полный администратор видит все подключения; сотрудник владельца с правом просмотра — подключения собственного теста; остальные — настройки текущего подразделения. Студент видит опубликованные тесты выбранного доступного подразделения без административных действий.

Полный администратор видит банк всей организации. Сотрудник с `tests.view` видит тесты текущего подразделения и тесты, открытые владельцами в банк. Создание, подключение и копирование требуют `tests.edit`. Просмотр чужих попыток и сдач требует отдельного `test-results.view`; принудительная сдача и сброс — `test-results.edit`. Старый ключ `test_results` используется только при отсутствии канонического `test-results`; отозванное каноническое право нельзя восстановить старым alias. Доступ к банку сам по себе не открывает чужие сдачи.

Сотрудник выбирает другое доступное подразделение через контекст auth. URL не расширяет его права. Каждый бизнес-вызов проверяет Bearer-токен через живую introspect-проверку auth; организация берётся из проверенного токена. Core проверяет принадлежность подразделений и направления организации. Недоступность зависимости закрывает доступ с `503`.

## Подключение, копия и публикация

Подключение сохраняет тот же ID и общее содержимое. Новое подключение скрыто, без дат и времени, с выключенным просмотром ответов. Повтор не создаёт дубликат. Закрытие банка не снимает существующие подключения; подключение владельца снять нельзя.

Независимая копия создаёт отдельный документ, владельца, единственное подключение, собственную неизменяемую версию вопросов и историю. Копируются название, описание, направление и весь набор вопросов с ключами и весами. Ревизия начинается с `1`; настройки публикации и банк выключены. Изменения исходника, его архивирование и будущие сдачи не изменяют копию. `origin` хранит справочное происхождение.

Название — до 200 символов, описание — до 2000. Даты RFC3339 с часовым поясом сохраняются в UTC, задаются вместе; конец позже начала. Время прохождения — 0–1440 минут, проходной процент — 0–100 либо `null`. Публикация требует дат, положительного времени и хотя бы одного корректного вопроса. Скрытый тест может быть пустым для промежуточного сохранения редактора.

Архив закрывает прохождение и просмотр ответов во всех подразделениях. Восстановление сохраняет настройки. `actions`, `is_owner`, `is_attached` и `origin` предназначены для карточки; каждый метод самостоятельно проверяет права независимо от этих флагов.

## Вопросы, версии и история

Вопрос содержит `question_id`, `type`, `text`, `points`, `answers` и `correct_answers`:

```json
{"question_id":1,"type":"single","text":"Выберите ответ","points":5,"answers":[{"id":"a","text":"Первый","is_correct":true},{"id":"b","text":"Второй","is_correct":false}],"correct_answers":[]}
```

`single` имеет минимум два варианта и ровно один правильный. `multiple` имеет минимум два варианта и минимум один правильный. `text` содержит непустые допустимые ответы в `correct_answers` без вариантов. Веса — положительные целые до 100000. Количество вопросов, вариантов выбора и текстовых ответов не ограничено бизнес-валидацией. Текст вопроса — до 4000 символов, текст варианта — до 2000, отдельный текстовый ответ — до 1000; ограничения размера транспорта/хранилища применяются отдельно.

ID вопросов — уникальные положительные целые в безопасном для JavaScript диапазоне. Новый вопрос после сохранения получает ID больше исторического `max_question_id`. Удалённые ID вопросов и вариантов не используются повторно. `GET content` возвращает `max_question_id` и `used_option_ids` для редактора. ID вариантов допускают `A-Za-z0-9_-`, длина 1–128.

Сохранение редактора создаёт одну неизменяемую версию и один пакет изменений: автор, время, версии до/после, полные снимки реквизитов и вопросов, добавленные/удалённые/изменённые вопросы, изменение порядка и реквизитов. Изменение ключа, веса, текста, типа или вариантов входит в значения до/после. Изменение реквизитов через обычный `PUT /{test}` тоже создаёт версию. Совпадающее содержимое не меняет ревизию и не создаёт событие.

История читает версии, включённые в подтверждённую историю теста. Кандидат версии после проигранной параллельной записи не попадает в историю и не отправляется в RabbitMQ. Calculate применяет политику пересчёта к подтверждённым изменениям; каждая проверка использует отдельный неизменяемый вход.

Администратор с доступом к тесту читает полный `content` и историю с ключами. Студенческий DTO содержит текст, тип, вес и тексты вариантов; ключей `is_correct` и `correct_answers` нет. Студент получает вопросы через свою попытку. Списки и карточки возвращают только `question_count` и `content_version_id`.

## Черновики

Черновик хранит незавершённые вопросы и координаты `layout: [{question_id,x,y}]`. Допускаются пустое название, отсутствие направления и нулевые веса. Такие данные не проходят проверку публикации.

Редактирование и публикация требуют своей действующей блокировки на 90 секунд. Получение или продление блокировки возвращает новую ревизию. Другой редактор получает `409`; истёкшую блокировку можно забрать. Снятие своей блокировки и архивирование доступны отдельными методами.

Публикация создаёт новый самостоятельный скрытый тест и переводит черновик в `published`. Сначала атомарно закрепляется состояние `publishing`, версия черновика и ID будущего теста; затем создаётся тест. Сбой между шагами восстанавливается повтором с той же исходной ревизией. Редактирование закреплённого черновика закрыто. Повтор завершённой публикации возвращает тот же тест с `200`.

## Прохождение и офлайн-доставка

Старт создаёт попытку либо возвращает существующую активную попытку того же подразделения. Фиксируются неизменяемая версия содержимого, случайный порядок вопросов, время старта, окончание ответов и срок загрузки. Повторный старт не перемешивает вопросы и не продлевает время. Изменения теста после старта не заменяют вопросы начатой попытки.

Время ответов равно времени старта плюс лимит настройки при старте. Финальный снимок можно доставить до 24 часов после этого срока. Сервер проверяет время фиксации ответа/завершения. Клиент хранит черновики, коммиты и финальный снимок локально до подтверждения сервера, прекращает изменение ответов при окончании времени и повторяет доставку при восстановлении связи.

Для начатой официальной попытки `access` и `catalog-with-access` используют закреплённые сроки попытки: `resume_attempt` до срока ответов включительно, `pending_upload` после него до срока доставки включительно, `upload_deadline_passed` после срока доставки. В последнем случае `official_access_allowed=false`, даже если общий период начала теста ещё открыт. Принятая сдача сохраняет `already_submitted`. Сроки карточки берутся из `answer_deadline` и `upload_deadline` соответствующей попытки; общий конец периода теста не заменяет срок доставки. Клиент показывает точные дату и время по Москве, а после закрытия доставки — номер попытки и инструкцию обращения к администратору.

Одиночная или пакетная фиксация блокирует ответ от изменения. Повтор идентичного значения безопасен. `commits` принимает до 25 записей: `commit_id`, `sequence`, `question_id`, `value`, `answered_at`. Повтор ID с теми же данными подтверждается; другой ответ или повтор номера последовательности с другим коммитом даёт `409`.

Финальный снимок — авторитетные ответы, включая локальные ответы, ещё не доставленные промежуточными коммитами:

```json
{"test_version_id":"507f1f77bcf86cd799439011","completed_at":"2026-10-07T12:00:00.000Z","reason":"manual","answers":[{"question_id":1,"value":"a"},{"question_id":2,"value":["a","c"]},{"question_id":3,"value":"Текст ответа"}]}
```

Для `single` значение — ID варианта; для `multiple` — массив уникальных ID, нормализуемый сортировкой; для `text` — строка. Пропущенный вопрос допускается как вопрос без ответа. Причина — `manual` или `timeout`. `snapshot_hash` необязателен. Если передаётся, это SHA-256 исходного JSON без поля `snapshot_hash`: ключи объектов рекурсивно сортируются, массивы сохраняют порядок, JSON кодируется компактно в UTF-8 без экранирования HTML и непробельных Unicode-символов. Строки даты сохраняют исходный часовой пояс и формат. Сервер дополнительно сохраняет собственный хеш нормализованного смыслового снимка для повторов. Повтор того же снимка возвращает ту же сдачу, изменённый снимок — `409`. После принятия срок загрузки не мешает получить подтверждение повторной доставки.

Принятие одной атомарной записью закрепляет ответы, ID сдачи, статус `accepted`, `calculation_status=queued` и исходящее сообщение. Ответ возвращается сразу:

```json
{"status":true,"data":{"submission_status":"accepted","calculation_status":"queued","division_id":1001,"result":null,"status_url":"/v1/tests/submissions/507f1f77bcf86cd799439012"}}
```

Для интерфейса это «Проверка ответов» в конкретной сдаче. У общего теста глобального статуса проверки нет. `null` означает отсутствие результата, а не ноль баллов. Недоступный RabbitMQ не отменяет принятую сдачу; сообщение остаётся в Mongo. Ошибка сохранения не подтверждает приём, и клиент сохраняет локальный снимок для повтора.

`submit` из серверных ответов и административный `force-submit` используют тот же асинхронный путь. Сброс сохраняет старую попытку как `reset`, снимает активную уникальность и повышает ревизию расчёта. Поздний результат старой сдачи не восстанавливает сброшенную попытку.

Тренировка доступна при разрешённом просмотре ответов после принятой официальной сдачи либо после окончания окна теста. Она использует отдельную попытку, немедленную обратную связь calculate и собственные ответы; официальной сдачи и сообщения на рейтинг не создаёт. Правильный одиночный вариант, точное множество вариантов или совпадение с одним текстовым ответом после удаления крайних пробелов и приведения к нижнему регистру дают весь вес; иначе — ноль. Частичных баллов нет.

`POST /attempts/{attempt}/submit` завершает тренировку с `200`, статусом `practice_completed` и суммарным тренировочным результатом. Повтор безопасен. Завершённая тренировка снимает активную уникальность, поэтому следующая тренировка создаёт новую попытку. Официального `submission_id` и сообщения RabbitMQ у неё нет.

Разбор официальной сдачи открывается после готового результата. Студенту требуется разрешённый просмотр ответов выбранного подключения. До готовности — `409 calculation_pending`; без права просмотра — `403`. Обычный статус результата не раскрывает правильные ответы.

## HTTP

Локальный [OpenAPI с DTO](http://127.0.0.1:8004/openapi.json). Ответы: `{ "status": true, "data": ... }`; ошибки: `{ "status": false, "error": "..." }`. ID аккаунтов — `account_id` auth; ID тестов, версий, черновиков, попыток и сдач — 24-символьные Mongo ObjectID. Неизвестные поля и лишний JSON отклоняются; максимум запроса — 1 MiB.

| GET / PUT | `/{test}/content` | Содержимое / сохранение редактора |

| GET / POST | `/divisions/{division}/tests` | Список / создание с вопросами |

Изменения требуют `expected_revision`; конфликт — `409 stale_revision`. `PUT content` передаёт весь набор `title`, `description`, `direction_id`, `questions`. Обычный `PUT /{test}` сохраняет вопросы, если `questions` отсутствует. `PUT settings` заменяет все настройки подключения: `published`, `start_at`, `end_at`, `time_limit_minutes`, `passing_score`, `answers_visible`. Пропущенные boolean становятся false, nullable-настройки — null.

Создание теста, независимой копии и черновика, включая черновик из теста, требует `Idempotency-Key`: 16–128 символов `A-Za-z0-9_-`. Другая операция или тело с тем же ключом в области хранения — `409 idempotency_conflict`. Повтор возвращает текущий созданный документ. Публикация черновика повторяется по исходной `expected_revision` и закреплённому ID.

Пагинация: `limit` 1–100, по умолчанию 20; `offset` 0–100000. Каталог поддерживает `q`, `direction_id`, `owner_division_id`, `is_archived`, `relation=all|owned|attached|copy`; фильтры пересекаются. `target_division_id` в банке и карточке задаёт контекст действий без расширения доступа сотрудника. Попытки и сдачи поддерживают `test_id`; административные списки — `account_id`; попытки — `practice=true`; сдачи — `calculation_status=queued|processing|retrying|ready|failed`. Черновики: `state=draft|publishing|published|archived`, по умолчанию `draft`.

Список сдач и его статистика применяют одинаковые фильтры `test_id`, `account_id` и `calculation_status`. Фильтр аккаунта администратора учитывается до подсчёта статистики; ученик всегда ограничен собственным аккаунтом. `practice` принимает только `true`/`false`; неизвестное значение возвращает `400`.

## Хранение и сообщения

Сервис владеет коллекциями `tests_catalog_v1`, `tests_content_versions_v1`, `tests_drafts_v1`, `tests_attempts_v1`, `tests_calculation_jobs_v1`. Сдача хранится в документе попытки вместе с ответами и outbox; межколлекционная транзакция для принятия не требуется. Содержимое, история и событие редактора подтверждаются CAS-записью каталога. Mongo standalone поддерживается; записи подтверждаются majority + journal. Старые коллекции exam и их данные не переносятся и не меняются.

Outbox передаёт постоянные сообщения с publisher confirms и обязательной маршрутизацией в долговечный topic exchange `cpm.events`. Quorum-очередь `calculate.events.v1` привязана к `tests.grade.requested.v1` и `tests.content.changed.v1`. После подтверждения брокера сообщение удаляется из outbox. Сбой между подтверждением и удалением может дать повтор; calculate подтверждает его после идемпотентной записи в собственный inbox по `message_id`.

Конверт: `message_id`, `message_type`, `schema_version=1`, `occurred_at`, `producer=tests-service`, `correlation_id`, `payload`. Официальная сдача передаёт ID задания/сдачи/попытки/теста, организацию, конкретное подразделение, аккаунт, версии попытки и проверки, ревизию расчёта и хеш входа. Полный неизменяемый снимок ответов, порядка и вопросов с ключами сохраняется до атомарного выбора задания в документе попытки и доступен через внутренний input API. Изменение теста передаёт весь `change_batch` с полными значениями до/после и фиксированными версиями. В change_batch фиксируются event_id, recalculate_on_test_change и organization_settings_revision. Calculate определяет необходимость пересчёта; tests готовит задания для активных официальных сдач всех подключённых подразделений постранично по 50 записей.

Calculate не записывает напрямую в хранилище tests. Используются внутренние методы с `X-Service-Key`:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/internal/tests/submissions/{submission}/input?calculation_revision=N` | Неизменяемый вход текущего задания; устаревшая ревизия — 409 |
| POST | `/internal/tests/submissions/{submission}/result` | Результат соответствующей ревизии расчёта |
| POST | `/internal/tests/submissions/{submission}/calculation-status` | processing/retrying/failed текущей ревизии; готовый результат не понижается |
| POST | `/internal/tests/recalculations/prepare` | Повторяемая подготовка страницы пересчёта подтверждённой версии |
| POST | `/internal/tests/ratings/snapshot` | Текущие тесты и официальные результаты области для сервиса ratings |

Результат содержит `calculation_revision`, `input_hash`, `grading_test_version_id`, `excluded_question_ids`, `score`, `earned_points`, `max_points`, `question_results: [{question_id,points,is_correct}]`. Проверяются полнота вопросов, веса и согласованность процентов. Идентичный повтор безопасен; другой результат готовой ревизии — `409`; сброшенная сдача или устаревшая ревизия — `409`. Calculate сохраняет вычисленный результат в своём inbox до callback. Tests резервирует неизменяемый результат в задании и атомарно сохраняет балл с ссылкой на историю в той же попытке. История содержит одну запись на подтверждённую ревизию, включая повторы после потери ответа. Ответы, snapshot_hash, исходная версия, подразделение и ID сдачи не меняются. Кандидаты заданий после проигранного CAS не считаются подтверждённой историей.

Tests не читает чужие MySQL-таблицы. Core предоставляет `POST /internal/core/test-references` с сервисным ключом и проверяет организационные ссылки. Пользовательский токен не заменяет сервисный ключ. Секреты приходят из окружения; dev-конфигурация — игнорируемый `dev/local/tests.env`. Tests запускается без root с read-only файловой системой. Готовность приёма зависит от Mongo, auth и core; RabbitMQ обслуживает outbox, а синхронная тренировка требует calculate.

## Правила баллов и пересчёта

Официальный расчёт использует те же правила, что тренировка: весь вес вопроса либо ноль, точное совпадение множества вариантов и нормализация текста как Python strip().lower(). Неотвеченные вопросы входят в исходный максимум с нулём баллов. Процент повторяет старое `int(round(earned / maximum * 100, 2))`, включая порядок операций и округление; пустая область пересчёта даёт earned_points=0, max_points=0 и score=0.

Пересчёт запускают удаление вопроса, смена его типа или веса, изменение признака правильности существующего варианта, удаление любого варианта, удаление или добавление допустимого текстового ответа у существующего вопроса. Изменения реквизитов, формулировок или порядка, добавление вопросов и вариантов выбора сами по себе его не запускают. Добавление текстового ответа — расширение прежней политики: например, сохранённая «Москва» становится верной после добавления «Москва» к ключу «Питер». См. [матрицу пересчёта](../calculate/docs/test-recalculation-matrix.md).

При пересчёте рассматриваются только вопросы исходной сдачи. Новые вопросы не увеличивают её максимум; удалённые вопросы и вопросы с изменённым типом исключаются. Изменение типа необратимо исключает исторический ответ, даже если тип позже возвращён. Исторически выбранный удалённый вариант даёт ноль. Совместимость определяется по всей подтверждённой истории до выбранной версии.

Core хранит организационную настройку: `GET /v1/core/organization/test-settings` и `PUT` по тому же пути с `{expected_revision, recalculate_on_test_change}`. По умолчанию значение true; менять его может полный администратор организации. Сервисный `GET /internal/core/organizations/{organization}/test-settings` вызывается перед сохранением изменения. Недоступность настройки не подтверждает сохранение редактора.

Выключенная настройка сохраняет прежние баллы при редактировании. Включение само по себе не пересчитывает прошлые изменения; следующее подходящее редактирование использует выбранную новую версию и историю совместимости. Уже сохранённое событие использует зафиксированное значение настройки. При подготовке выбираются сдачи с persisted accepted_at не позже changed_at события; поздняя офлайн-сдача проверяется по исходной версии. Более старая версия не может заменить уже назначенную новую проверку.

Во время расчёта/пересчёта текущий result равен null, предыдущий балл остаётся в административной истории. Статусы: queued → processing → ready; при временной ошибке retrying, при постоянной failed. Восстановление calculate продолжает принятые сообщения и страницы без повторного ручного запуска. Общий рейтинг по нескольким тестам — отдельный процесс.

## Снимок для рейтинга

`POST /internal/tests/ratings/snapshot` требует `X-Service-Key`; пользовательский Bearer не предоставляет доступ. Строгий JSON-запрос:

```json
{"organization_id":1001,"division_id":1001,"date_from":"2026-10-01","date_to":"2026-10-31","as_of":"2026-10-08T12:00:00Z"}
```

Даты включительны и относятся к московскому календарю; `as_of` обязателен в RFC3339 UTC. Сохраняется отбор прежнего рейтинга: текущее опубликованное подключение выбранного подразделения, неархивный тест, московская дата начала внутри периода. Конец окна и наступление старта к `as_of` не добавляют фильтров. Принадлежность подразделения и направления организации проверяется через core `test-references`; название направления приходит из core, включая архивное направление для исторического отображения. В тестовом снимке нет ФИО, ответов и ключей вопросов.

Ответ в штатном `{status:true,data:...}`:

```json
{"source":"tests","organization_id":1001,"division_id":1001,"tests":[{"test_id":"507f1f77bcf86cd799439011","title":"Тест","direction_id":1001,"direction_name":"Математика","start_at":"2026-10-07T12:00:00Z","published":true,"is_archived":false,"results":[{"account_id":1002,"submission_id":"507f1f77bcf86cd799439012","calculation_revision":1,"calculation_status":"queued","score":null}]}],"external_tests":[],"external_source_version":"<64 hex characters>","external_domain":{"schema_version":1,"status":"ready","organization_id":1001,"division_id":1001},"input_hash":"<64 hex characters>"}
```

Для каждого теста возвращаются только текущие активные официальные `accepted` сдачи именно выбранного подразделения. Тренировки, сброшенные попытки и результаты других областей исключены. Готовый ноль возвращается как `score:0`; `queued`, `processing`, `retrying`, `failed` возвращаются с `score:null` даже при наличии старого балла. Отсутствующая сдача отсутствует в `results` и трактуется рейтинговым алгоритмом; тест без сдач остаётся с `results:[]`. Неоднозначные или неполные готовые данные дают `409 rating_source_incomplete`.

Внешние работы принадлежат одному подразделению и выбираются по московской дате `date` внутри периода, включая будущие даты. Snapshot включает их текущие результаты, идентификаторы и ревизии теста/строк; ноль, явный неизвестный балл и отсутствие строки различаются. `external_source_version` меняется при изменении реквизитов или ревизии результата, даже если числовой балл остался прежним. После проверки созданного владельцем marker возвращается scoped `external_domain`; отсутствующий или повреждённый домен даёт `503 external_domain_unavailable`, а исправный пустой каталог — `external_tests:[]`.

Тесты сортируются по ID, результаты — по `account_id`. SHA-256 `input_hash` считается по каноническому JSON полей `source`, `organization_id`, `division_id`, `tests`, `external_tests`, `external_source_version`, `external_domain`; ключи объектов сортируются рекурсивно, массивы сохраняют уже определённый порядок. Хеш не включает `input_hash` и время запроса. В пределах вызова выполняются два ограниченных чтения внутренних/внешних каталогов, официальных сдач и ссылок core; различие хешей даёт `409 rating_source_changed`. Это оптимистическая проверка текущих значимых данных, а не распределённая транзакция или исторический снимок на `as_of`: изменения после второго чтения требуют повторной проверки в ratings перед публикацией. Ratings сохраняет полученный вход в своём хранилище и повторяет запрос для проверки его актуальности.

Пределы одного снимка: 1000 внутренних и внешних тестов суммарно, 2000 различных аккаунтов, 100000 результатов, 16 MiB канонического JSON и 16 MiB проекции каждой Mongo-выборки; превышение — `413 rating_snapshot_too_large`. Читаются только нужные поля Mongo, без содержимого вопросов и ответов. Внешний каталог реализован в собственных коллекциях Tests; существующие данные старого MySQL автоматически не мигрируются. Контракты: [внешний домен](docs/external-tests-handoff-2026-10-09.md), [готовность снимка](docs/external-readiness-contract.md), [JSON-импорт](docs/json-import-contract.md), [кэш и каталог с доступностью](cache.md).

## Запуск и проверки

Из корня CPM сначала поднять dev:

```sh
./dev/dev tests-up
```

Затем выполнить проверки:

```sh
dev/.venv/bin/python services/tests/scripts/http_test.py
dev/.venv/bin/python services/tests/scripts/workflow_test.py
dev/.venv/bin/python services/tests/scripts/grading_test.py --faults
dev/.venv/bin/python services/tests/scripts/acceptance_race_test.py
dev/.venv/bin/python services/calculate/scripts/http_test.py
dev/.venv/bin/python services/core/scripts/http_test.py
dev/.venv/bin/python dev/scripts/verify.py
```

Go-проверки выполняются в `services/tests` и `services/calculate`: `go test -race ./...` и `go vet ./...`.

HTTP-проверки ограничены локальным dev и создают собственные вымышленные роли, пользователей, подразделения и тесты через API. Проверяются права, организационные границы, подключения и копии, вопросы и история, черновики и блокировки, закреплённый порядок, офлайн-повторы, принятие и сообщения, результат/разбор, сброс и разделение подразделений. Проверки удаляют только собственные предметные записи. Отчёты без секретов сохраняются в `dev/local`.

Контракты подключения React UI через локальный BFF, различия прежних DTO и полная матрица проверок описаны в [интеграции tests](../bff/tests-integration.md). `services/bff/scripts/tests_http_test.py` проверяет сценарии через BFF и создаёт fixtures только публичными API; `--queue-outage` дополнительно последовательно проверяет pause/recovery локальных calculate и Rabbit. Этот вариант запускается без параллельных пишущих сценариев; он всегда снимает свою pause в `finally`. Прежние service scripts включают direct-Mongo clock fixtures/cleanup, поэтому не подходят для режима проверки без прямой записи в БД. Суммарные рейтинги по нескольким тестам, перенос старых данных и нагрузочная проверка на 450 пользователей относятся к следующим этапам.

## HTTP-проекция для сервиса cards

Добавлены service+Bearer endpoints `/internal/tests/cards/catalog`, `/internal/tests/cards/tests/{test}` и `/internal/tests/cards/drafts`. Проекция использует действующий `practiceEligible`, не выдаёт скрытые/неразрешённые ответы. Ученик получает объединение доступных подключений своей организации, подтверждённых `division_ids` живого auth introspect; staff использует только выбранный контекст с явным разрешением train/cards/training. Прогресс при этом принадлежит cards и не делится по подразделениям. `catalog?admin=true` возвращает только опубликованные метаданные/счётчики, без вопросов. Создание черновика требует дополнительно tests.edit, активного направления и выбранного разрешённого подразделения; используется штатный Idempotency-Key. [Подробный контракт, отличие от прежнего visible-only доступа и HTTP-проверки](../cards/README.md).
