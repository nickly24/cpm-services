# CPM Auth — Go

Первый самостоятельный backend-сервис нового контура. Использует Go 1.27.1, стандартный HTTP-сервер, MySQL и подписанные JWT RS256. Встроенных ограничений попыток входа и Redis нет. Rate limit будет на внешнем входе по отдельной настройке.

Пул MySQL допускает 20 открытых соединений. Проверки паролей выполняются до 12 одновременно; остальные запросы ожидают свободный слот с учётом отмены запроса. Это ограничение памяти вычислений, а не rate limit входов. Production-контейнер имеет лимит 1 ГиБ и `GOMEMLIMIT=768MiB`.

## Что работает

- Вход для `student`, `proctor`, `examinator`, `supervisor`, `admin`, `staff_admin`.
- Проверка существующих хешей Werkzeug: PBKDF2-SHA256 и scrypt. Открытые пароли не принимаются; перед будущим переносом такие аккаунты потребуют отдельного преобразования или сброса пароля.
- Получение организаций и доступных подразделений. Один аккаунт ученика может участвовать в нескольких организациях.
- Выбор организации и подразделения при входе, переключение контекста с новым access-токеном.
- У администратора полные права в собственной организации. У `staff_admin` права просмотра/редактирования определяются ролью в выбранном подразделении.
- Access-токен на 15 минут, refresh-токен с ротацией; срок сессии 14 дней с момента входа. В БД хранятся только SHA256-хеши refresh-токенов. Повторное использование уже заменённого refresh-токена отзывает всю сессию.
- Проверка текущей сессии, выход, отключение аккаунта и отзыв через изменение версии доступа.
- Публичный ключ для BFF и сервисов через JWKS. Проверяются алгоритм, подпись, issuer, audience и срок действия JWT.

JWT подписан, но не зашифрован: его содержимое читаемо. В нём нет паролей и refresh-токенов. Закрытый ключ хранится отдельно от исходников, образа и настроек старого backend.

## Локальный запуск

Сервис доступен по `http://127.0.0.1:8002`. Все команды ниже выполняются из корня проекта `cpm`.

```sh
./dev/dev up
dev/.venv/bin/python services/auth/scripts/dev_setup.py
cd services/auth
go run ./cmd/keygen ../../dev/local/auth-private.pem
cd ../..
./dev/dev auth-up
./dev/dev status
```

Docker Desktop должен быть запущен и первоначальная настройка завершена. `auth-up` собирает образ, переносит dev-ключ в именованный том `cpm-dev_auth-keys` и запускает сервис. Ключ доступен контейнеру только для чтения, приложение работает без root. Команды `status`, `logs`, `stop` учитывают auth. После `stop` для повторного запуска всего auth-контура используйте `auth-up`.

Для разработки без контейнера auth:

```sh
cd services/auth
go build -o ../../dev/local/auth-run ./cmd/auth
cd ../..
dev/.venv/bin/python services/auth/scripts/run_local.py
```

Не запускайте одновременно два экземпляра на порту 8002. `run_local.py` явно загружает `dev/local/auth.env`, проверяет локальный адрес и запускает Go-бинарник. У сервиса нет production-реквизитов по умолчанию.

## API

Все тела запросов — JSON, все токены передаются как `Authorization: Bearer ...`. Ответы авторизации запрещены к кешированию. Cookies и доступ браузеров через CORS будет обслуживать BFF; эти маршруты предназначены для вызова через него или прямого dev-тестирования.

| Метод и адрес | Назначение |
|---|---|
| `POST /v1/auth/login` | Вход: `login`, `password`; необязательные `organization_id`, `division_id` |
| `GET /v1/auth/me` | Текущий пользователь, активный контекст и доступные организации/подразделения |
| `POST /v1/auth/context` | Выбор контекста: `organization_id`, `division_id` |
| `POST /v1/auth/refresh` | Обновление: `refresh_token` |
| `POST /v1/auth/logout` | Отзыв текущей сессии |
| `POST /v1/auth/introspect` | Проверка Bearer-токена с актуальными правами и состоянием сессии |
| `GET /.well-known/jwks.json` | Открытый ключ проверки подписи |
| `GET /openapi.json` | Контракт OpenAPI 3.1 для импорта в Postman и других клиентов |
| `GET /health/live`, `GET /health/ready` | Состояние процесса и готовность БД |

Алиасы `POST /api/auth`, `/api/aun`, `/api/logout` помогают сохранить знакомые адреса и ключи ответов. Это не полная совместимость со старым frontend: новый JWT использует RS256, cookie не устанавливается, а старые приложения пока не подключены к сервису.

При входе без выбранного контекста используется первая доступная организация и её первое доступное подразделение в порядке номеров. Администратор может выбрать организацию без подразделения; остальные пользователи работают в выбранном подразделении. Если при входе задано только название аккаунта и организация, для обычного пользователя выбирается её первое доступное подразделение. Передача подразделения при входе требует указать организацию.

Ответ входа содержит `status`, `token` (алиас `access_token`), `token_type`, `expires_in`, `refresh_token`, `user`, `organizations`. При смене контекста refresh-токен остаётся прежним и повторно не возвращается. Новый access-токен заменяет прежний на стороне клиента.

Ошибки: 400 — некорректные данные, 401 — неверные реквизиты/токен, 403 — нет выбранного контекста, 415 — требуется JSON, 503 — БД недоступна. Сервис не отвечает 429 из-за числа попыток входа.

## Контекст и границы доступа

`sub` — уникальный номер аккаунта, `id` — существующий номер профиля в пределах роли. Токен содержит `role`, `organization_id`, выбранный `division_id`, разрешённые `division_ids` **только активной организации**, `group_id` выбранного участия, `organization_admin`, административную роль и её `permissions`. Полный список организаций и подразделений возвращается отдельно в ответе, а не раздувает токен.

Для обычных ролей пустой `permissions` не запрещает их предметные действия: предметный сервис проверяет роль и её собственные ограничения — свою группу, комиссии, назначения и т. п. Для `staff_admin` права по разделам явные; редактирование подразумевает просмотр.

Auth проверяет сессию и актуальный доступ через БД на `me`, `context`, `introspect`, `logout`, `refresh`. После смены контекста прежний access-токен этой сессии не проходит такую проверку. После отключения аккаунта, снятия активного доступа или выхода доступ также отзывается.

**Проверка только подписи JWT в будущем BFF не даёт мгновенного отзыва:** такой токен остаётся криптографически действительным до истечения 15 минут. Для немедленной проверки используйте `introspect`; кеширование/распространение отзыва будет отдельным решением при разработке BFF. При изменении пароля или прав необходимо увеличивать `auth_account_state.auth_version`; старые access- и refresh-токены после этого отвергаются auth. Старое `session_version` ограниченного администратора также проверяется.

## Данные и границы первого этапа

Auth читает текущие dev-аккаунты и профили из копии прежней структуры. Добавлены девять таблиц для организаций, подразделений, доступа, ролей и сессий. Организации и подразделения пока являются локальной заготовкой будущего core; при его выделении их владение и получение контекста будут перенесены в согласованный контракт. Auth не создаёт организации, учеников и роли через публичные маршруты первого этапа.

`dev_setup.py` подключается только к `127.0.0.1:13306/cpm_dev` и создаёт вымышленные данные. Исходные 20 dev-аккаунтов сохранены в основном подразделении; для отдельных сценариев добавлены участия в резерве и другой организации. Всего 29 аккаунтов, из них 5 намеренно не проходят вход. Пароль находится в `dev/local/accounts.json`, перечень сценариев — в `dev/local/auth-seed-complete.json`. Один аккаунт с открытым паролем создан только как отрицательный тест совместимости и отвергается сервисом.

Seed не переписывает данные при повторном запуске. После удаления томов надо согласованно восстановить dev-БД и маркеры; самостоятельно маркеры не удаляются. Production, прежние приложения и MongoDB этот сервис не изменяет. Работа с рейтингом, снятие участия ученика и общий учебный контент относятся к последующим этапам.

## Проверка

```sh
cd services/auth
go test ./...
go vet ./...
cd ../..
dev/.venv/bin/python services/auth/scripts/http_test.py
```

Python нужен только для подготовки и независимого HTTP-тестирования; работающий сервис написан на Go. Зависимости HTTP-тестирования зафиксированы в `dev/requirements.lock.txt`. Тесты обращаются к реальному HTTP-серверу и dev-БД, проверяют подпись через публичный JWKS, все роли, изоляцию организаций, различные права подразделений, обновление, отзыв, неверные токены и отсутствие ограничений попыток. Временные изменения тестовых доступов восстанавливаются, созданные тестами сессии удаляются. Отчёт без токенов и паролей: `dev/local/auth-http-report.json`.

## Подключение core

Core проверяет каждый запрос через `/v1/auth/introspect`. Роли дополнены разделами `groups`, `directions`, `organizations`, `divisions`; `telegram-bot` исключён. Ограничений на число входов не добавлено.

Внутренний `POST /internal/auth/password-hash` требует `X-Service-Key`, равный `AUTH_INTERNAL_KEY` длиной не менее 32 символов. Без настройки endpoint закрыт; обычный пользовательский токен не даёт доступа. JSON `{ "password": "example-password" }`, 8–1024 байта; ответ `{ "hash": "pbkdf2:sha256:600000$..." }`. Секрет не передаётся frontend.

Первый dev core записывает профиль, созданный auth хеш, аккаунт и проекции доступа одной транзакцией в общей MySQL. [Граница сервисов и дальнейший административный API auth](../core/README.md). После `core-up` ключ для native-запуска auth также находится в `dev/local/auth.env`.

## Разрешения фонового импорта — исходники, 9 октября 2026

Контракт: [import-operation-grants-v1.md](docs/import-operation-grants-v1.md), Rev2.
После явного подтверждения Auth сохраняет неизменяемую привязку к аккаунту,
организации, подразделению, исходному файлу, нативной команде и точным байтам запроса.
Каждый вызов проверяет текущие права и `auth_version`; выход из одной сессии или
переключение кабинета не отменяет уже подтверждённое задание. Восстановление выдаёт
только разрешение прочитать квитанцию, сохраняя исходный ключ команды.
Отзыв запрещает последующие вызовы, но не откатывает сохранённые данные.

По умолчанию новые внутренние маршруты выключены. Включение требует отдельного
issuer key и четырёх owner keys, отличных друг от друга и от `AUTH_INTERNAL_KEY`;
неполная конфигурация останавливает запуск. TTL — 21600 секунд по умолчанию,
допустимо 300–86400. Приватные строки файла и bearer не сохраняются в Auth.

Подготовлены аддитивная миграция `003_import_operation_grants.sql`, отдельный
Dev runner `scripts/migrate_operation_grants.py` и optional overlay
`dev/compose.auth-operations.yaml`. Runner профиля `scripts/run_operation_profile.py`
читает приватный regular-файл `dev/local/import-operation-credentials.env` с mode0600,
проверяет десять различных ключей, запрещает подмену ключей окружением и меняет
только Auth. `--check --image sha256:<frozen-image-id>` проверяет файл без Docker.
Запуск принимает только неизменяемый SHA образа и не скачивает другую версию.
Миграция и включение выполняются в согласованном окне после финальных сборок;
наличие исходников не означает включённый Dev runtime или проверенную очередь.

Ни один из этих внутренних маршрутов не проксируется через публичный BFF.
Строгий JSON отклоняет повторные, неизвестные и неоднозначные поля; метаданные
идентификаторов передаются десятичными строками без потери точности JavaScript.

## Подробности отзыва контекста — 8 октября 2026

Access JWT содержит положительный `context_version`, соответствующий версии сессии.
Каждый успешный `/v1/auth/context` увеличивает её атомарно, в том числе при выборе
того же контекста. Все прежние поколения access остаются недействительными после
возврата A → B → A. Параллельные переключения по одному access имеют одного победителя;
второй запрос получает `401 invalid_token`. Клиент должен синхронизировать смену контекста
между вкладками, а не автоматически повторять её устаревшим access.

Refresh при переключении сохраняется. Ротация блокирует строку сессии и выпускает access
из её текущего контекста/версии; ошибка выпуска не расходует refresh. Более позднее
переключение может отозвать уже выпущенный access, но новый refresh остаётся пригоден.
Повторное использование заменённого refresh по-прежнему отзывает сессию.

Перед запуском обновлённого auth применить аддитивную миграцию только в local dev:

```sh
dev/.venv/bin/python services/auth/scripts/migrate_context_version.py
```

Скрипт идемпотентен, проверяет `cpm_dev` и локальный порт; меняет только новую auth-таблицу
`auth_sessions`, добавляя `context_version BIGINT NOT NULL DEFAULT 1`. Подготовка нового
контура `dev_setup.py` также применяет эту миграцию. Старые access без версии перестают
приниматься обновлённым auth; существующие refresh позволяют получить новый access
без повторного ввода пароля. Старую и новую версии auth нельзя использовать одновременно
на одном пользовательском входе: старая версия не проверяет поколение токена.

Регрессионная HTTP-проверка использует собственные сессии вымышленных dev-аккаунтов,
не меняет профили/права и не требует SQL-доступа:

```sh
dev/.venv/bin/python services/auth/scripts/context_regression_test.py --core
```

Проверяет все шесть ролей, A → B → A, смену организации, повтор текущего контекста,
отказ чужого контекста, сохранность/ротацию/replay refresh, logout, гонки переключений
и refresh, а также отказ старых access через неизменённый core.
Отчёт без секретов: `dev/local/auth-context-regression-report.json`.

Проверено на обновлённом dev auth `127.0.0.1:8002`: 255 HTTP-проверок с core,
`go test -race ./...` и `go vet ./...`. Отдельно подтверждён переход старой сессии
через существующий refresh. Заменён только контейнер auth; остальные десять
контейнеров сохранили идентификаторы и время запуска.
