# Calculate

Go-сервис на порту `8005` проверяет официальные сдачи и запускает пересчёт ранее принятых сдач после изменений теста. Tests принимает исходные ответы, отвечает клиенту `202`; calculate получает задачу через RabbitMQ, вычисляет результат и передаёт его внутреннему API tests. Балл сохраняет сервис tests в своей записи сдачи. При включённой интеграции ratings отдельный исполнитель также считает персональные рейтинги. Calculate пишет только собственные Mongo-коллекции `calculate_inbox_v1` и `calculate_ratings_inbox_v1`.

Сдача и задача сохраняют `organization_id`, `division_id`, `account_id`, `test_id`. Область проверяется перед вычислением. Официальные результаты одного теста в разных подразделениях независимы; изменение общего содержания охватывает существующие сдачи из всех подразделений этого теста.

## Проверка ответов

Сохраняется алгоритм старого сервиса:

- `single`: выбран правильный ID — весь вес вопроса, иначе ноль.
- `multiple`: выбранное неупорядоченное множество точно совпадает со всеми правильными ID — весь вес, иначе ноль. Частичных баллов нет.
- `text`: крайние пробелы удаляются, текст приводится к нижнему регистру по Unicode и сравнивается целиком с одним из допустимых ответов. Сохранены расширение `İ` в `i` с комбинируемой точкой, контекстная греческая sigma и пробельные разделители Python `strip`.
- Пропущенный вопрос даёт ноль. При первоначальном расчёте максимальный балл включает все вопросы закреплённой версии.
- Процент — `int(round(earned / max * 100, 2))`, с прежним порядком float64-операций, округлением до двух знаков по банковскому правилу и усечением. Например, `399/20000` даёт `1`, `1/3` — `33`, `2/3` — `66`.

Исходные ответы, порядок вопросов, время завершения и версия прохождения неизменны. Результат хранится отдельно. Вопросы результата идут в порядке, выданном при старте попытки. Версия прохождения и версия проверки различаются после пересчёта.

## Пересчёт

Организационная настройка в core определяет, следует ли пересчитывать баллы после редактирования теста. Значение и версия настройки фиксируются tests в пакете изменений при сохранении. Изменение настройки после сохранения не меняет решение уже созданного события.

Политика перенесена из `test_recalc_policy.py`. Пересчёт запускают удаление вопроса, изменение его типа или веса, изменение `is_correct` у существующего варианта, удаление любого варианта ответа и удаление текстового допустимого ответа. Изменение типа исключает вопрос из старых сдач; остальные изменения того же вопроса отдельно не классифицируются.

Изменение названия, направления, формулировки, текста вариантов и порядка вопросов не запускает пересчёт. Добавление вопроса, варианта, включая правильный, или текстового допустимого ответа тоже не запускает его. Текстовые допустимые ответы сравниваются как исходные строки: изменение регистра или пробелов считается удалением прежнего ответа, даже если проверка нормализованного текста дала бы тот же балл.

Tests готовит неизменные задания из пакета изменений и исходной версии каждой сдачи. В исторический максимальный балл входят только вопросы исходной попытки, оставшиеся после исключений. Новые вопросы не добавляются. Удалённые вопросы и вопросы с изменённым типом исключаются; накопленные исключения сохраняются при последующих пересчётах. Если исключены все вопросы, результат — `score=0`, `max_points=0`. Выбранный когда-то вариант, удалённый из новой версии, сохраняется в исходных ответах и даёт ноль при пересчёте.

Каждое задание получает новую `calculation_revision`, `job_id`, `input_hash` и версию проверки. Повтор события не создаёт второе задание для той же сдачи и версии. Более старое событие не может понизить версию проверки. Callback старого задания или сброшенной сдачи отклоняется tests; calculate отмечает такое задание `skipped`.

## Доставка и восстановление

Долговечный topic exchange `cpm.events`, quorum-очередь `calculate.events.v1`, маршруты `tests.grade.requested.v1` и `tests.content.changed.v1`. Конверт:

```json
{
  "message_id": "bd095746-6c38-4b77-bc40-c6d0e62d1b2d",
  "message_type": "tests.grade.requested",
  "schema_version": 1,
  "occurred_at": "2026-10-07T12:00:00Z",
  "producer": "tests-service",
  "correlation_id": "operation-123",
  "payload": {
    "submission_id": "507f1f77bcf86cd799439011",
    "test_id": "507f1f77bcf86cd799439012",
    "organization_id": 1001,
    "division_id": 1001,
    "account_id": 42,
    "calculation_revision": 1,
    "operation": "initial_grade",
    "grading_test_version_id": "507f1f77bcf86cd799439013"
  }
}
```

Допустим `causation_id`. Операция повторного расчёта — `regrade`. Изменение теста содержит идентификаторы до/после и полную `change_batch` с исходными и новыми вопросами. Calculate сохраняет точные байты конверта и SHA-256 конверта и канонического payload. `_id` уникален. ACK отправляется только после подтверждённого Mongo-записывания с `majority` и journal. Повтор тела ACK-ается без новой записи. Неизвестная версия/тип, неправильный маршрут, дубли JSON-ключей, превышение 4 MiB и повтор ID с другим телом отправляются в quorum-очередь ошибок `calculate.events.dead.v1` через `cpm.events.dead`.

Сохранённую inbox читают ограниченные пулы: по умолчанию четыре исполнителя только для новых сдач (`initial_grade`) и один отдельный исполнитель для подготовки пересчёта (`content`) и его заданий (`regrade`). Два фоновых вида работы делят один слот и чередуются, поэтому массовый пересчёт не занимает слоты новых сдач. Персональные рейтинги сохраняют отдельный исполнитель и inbox.

Каждый исполнитель атомарно захватывает запись на 60 секунд. Запросы отдельно обходят `received`, готовые `retrying` и просроченные `processing`, чередуя приоритет статусов. Индекс `inbox_schedule` (`processing_kind,status,available_at,_id`) обеспечивает порядок без общей сортировки всех ожидающих записей. Повтор и восстановление lease не голодают за потоком новых заданий. Потеря процесса освобождает работу по истечении lease; прежний владелец после повторного захвата не может сохранить checkpoint, статус или результат. При штатной остановке сервис дожидается всех исполнителей и ограниченной записи состояния отменённых работ в `retrying`.

При старте метаданные расписания добавляются только активным старым сообщениям, включая принятые предыдущей версией в режиме `receipt_only`; завершённая история и точные байты конверта не меняются. Служебный retry также восстанавливает метаданные старого сообщения. Старые `lease_until`/`next_attempt_at` остаются обязательными ограничениями даже при наличии нового `available_at`, чтобы новый исполнитель не отобрал действующий lease у ещё работающей прежней версии.

Rabbit-потребитель также использует ограниченный пул записи: по умолчанию четыре сообщения параллельно, prefetch — удвоенный размер пула. ACK каждого сообщения следует за собственным подтверждённым Mongo-записыванием; `multiple=false`. Ошибка хранения или закрытие канала отменяет остальные записи и дожидается их окончания до переподключения, а неподтверждённые сообщения возвращаются в очередь. Это сохраняет идемпотентность при потерянном ACK и ограничивает память и число горутин.

Статусы: `received` → `processing` → `ready`; временный сбой — `retrying`; отключённый/ненужный пересчёт, сброшенная сдача или устаревшая версия — `skipped`; ошибочное содержимое задания или конфликт результатов — `failed`. Сетевая ошибка и HTTP `429`/`5xx` повторяются без ограничения числа попыток, с экспоненциальной задержкой до 32 секунд и случайным разбросом от половины до полного интервала. Переподключения Rabbit также распределены по случайному интервалу. При ошибке Mongo работа остаётся в inbox. Статусы официального расчёта передаются tests с проверкой текущей версии и хеша; уже готовый результат не возвращается в `processing`.

Вычисленный результат записывается в inbox **до** callback. Если tests сохранил балл, а HTTP-ответ потерян, calculate повторно отправляет тот же сохранённый результат. Tests принимает идентичный callback без новой записи истории и отклоняет другой результат для уже завершённого задания. Подготовка большого пересчёта идёт страницами, с сохранением курсора; каждое новое задание получает собственное событие через outbox tests.

## Внутренние HTTP-методы

Все внутренние методы требуют `X-Service-Key`, совпадающий с `AUTH_INTERNAL_KEY`.

| Метод | Путь | Результат |
|---|---|---|
| GET | `/health/live` | Процесс работает, `mode=grading` |
| GET | `/health/ready` | Mongo, Rabbit-потребитель и tests доступны |
| GET | `/internal/calculate/messages` | Метаданные inbox, фильтры `submission_id`, `test_id`, пагинация `limit` 1–100 и `offset` 0–100000 |
| GET | `/internal/calculate/messages/{message_id}` | Неизменный payload и состояние обработки |
| POST | `/internal/calculate/messages/{message_id}/retry` | Тело `{}`; вернуть `failed`/`retrying` в `received`, сохранив вычисленный результат и курсор |
| POST | `/internal/calculate/practice/check` | Синхронная проверка одного тренировочного вопроса |
| POST | `/internal/calculate/practice/finish` | Синхронный результат всей тренировки |

Повтор операционного retry уже ожидающей записи возвращает `202`; отсутствующий ID — `404`; иной статус — `409`. Исправление официального расчёта выполняется через административный API tests: оно создаёт новую ревизию задания с теми же исходными ответами.

Calculate вызывает API tests:

- `GET /internal/tests/submissions/{id}/input?calculation_revision=N`: неизменный вход конкретного задания, область, операция, `input_hash`, версия проверки, эффективные вопросы, оригинальные ответы, порядок и накопленные исключения.
- `POST /internal/tests/submissions/{id}/result`: `calculation_revision`, `input_hash`, `grading_test_version_id`, `excluded_question_ids`, `score`, `earned_points`, `max_points`, `question_results`.
- `POST /internal/tests/submissions/{id}/calculation-status`: текущие ревизия/хеш, `processing`/`retrying`/`failed` и код причины.
- `POST /internal/tests/recalculations/prepare`: ID исходного события и теста, организация, версии до/после, решение политики, причины, исключённые ID и курсор. Tests проверяет принадлежность пакета истории теста и настройку, затем атомарно создаёт задания и их сообщения.

Список inbox исключает большое тело уже в Mongo-проекции. Ошибки не содержат адресов подключения, ключей или чужого текста ответа. Внутренний ключ не пересылается при редиректах.

Тренировка принимает `{question,value}` либо `{questions,answers:[{question_id,value}]}`. Проверяет типы, уникальность вариантов/ответов и известные ID. Даёт немедленный результат, не создаёт официальные сдачи, события или рейтинг. Неизвестный вариант в новой тренировке — `400`; допуск удалённого исторического варианта применяется только к `regrade`.

## Конфигурация и dev

Обязательны `MONGO_HOST`, `MONGO_PORT`, `MONGO_DATABASE`, `MONGO_USER`, `MONGO_PASSWORD`, `RABBITMQ_URL`, `AUTH_INTERNAL_KEY` длиной минимум 32 символа и `CALCULATE_TESTS_URL` (`http://tests:8004` в dev). HTTP разрешён для локальных tests; внешние подключения используют HTTPS. `MONGO_TLS=true` включает TLS. `CALCULATE_LISTEN_ADDR` по умолчанию `127.0.0.1:8005`; `CALCULATE_LISTEN` — алиас. Внешний RabbitMQ использует `amqps`.

`CALCULATE_GRADING_WORKERS` задаёт число исполнителей новых сдач: по умолчанию `4`, диапазон `1..32`; фоновый слот добавляется отдельно. `CALCULATE_RECEIPT_WORKERS` задаёт число одновременных записей Rabbit-потребителя: по умолчанию `4`, диапазон `1..8`. `CALCULATE_MONGO_POOL_SIZE` задаёт предел Mongo-соединений: по умолчанию прежние `10`, диапазон `2..128`. Эти значения ограничивают параллелизм, но сами по себе не определяют число поддерживаемых учеников; их выбирают по измерению задержек и ожидания соединений БД.

При запуске сервис создаёт только индексы собственной inbox: поиск сообщений сдачи/теста, совместимый `inbox_processing`, `inbox_schedule` для захвата работы и `inbox_monitoring` (`processing_kind,status,received_at,_id`) для количества/возраста ожидающих заданий. `Worker.Stats()` возвращает атомарные счётчики активных обработок, завершений, повторов, ошибок и суммарного времени по виду работы. `content` и `regrade` делят один слот, поэтому их capacity нельзя складывать. Docker работает под UID 65532. `/calculate healthcheck` проверяет `/health/ready`.

Опциональный `CALCULATE_RATINGS_URL` включает расчёт рейтингов; адрес и порт сервиса ratings задаёт dev Compose. Разрешены HTTP только для `ratings`, `localhost`, `127.0.0.1`, либо HTTPS без credentials/query/fragment и дополнительного пути. Без этого параметра интеграция рейтингов отключена, её коллекция и очереди не создаются. Включённая интеграция добавляет проверку доступности ratings и своего потребителя в `/health/ready`.

## Персональные рейтинги

Долговечная quorum-очередь `calculate.ratings.v1` привязана к `cpm.events` маршрутом `ratings.calculate.requested.v1`. У неё отдельные Rabbit-соединение, потребитель, Mongo inbox `calculate_ratings_inbox_v1` и вычислительный исполнитель. Проверка официальных сдач продолжает работать через прежнюю очередь и исполнитель. Формат некорректного или конфликтующего сообщения уходит в `calculate.ratings.dead.v1` через `cpm.events.dead` и маршрут `calculate.ratings.invalid.v1`.

Конверт имеет `schema_version=1`, `message_type=ratings.calculate.requested`, `producer=ratings-service`, UTC `occurred_at`, UUID `message_id`, непустой `correlation_id`; payload содержит только `{job_id,revision,organization_id,division_id,account_id,input_hash}`. Все ID области положительные, job — UUID, ревизия положительная, хеш — SHA-256. Никаких имён, ответов или оценок в сообщении нет. ACK следует за подтверждённой записью собственной inbox; повтор того же тела безопасен, другой payload с тем же message ID отвергается.

После захвата lease calculate получает `GET /internal/ratings/jobs/{job_id}/accounts/{account_id}/input` с `X-Service-Key`. Владелец передаёт неизменяемый персональный вход из `RatingInput`: идентификаторы области, `algorithm_version=legacy-rating-v1`, период, UTC `as_of`, домашние работы, выбранные тесты и эффективные результаты экзаменов. Calculate проверяет все идентификаторы против сообщения и заново вычисляет хеш: JSON разбирается с сохранением числовых литералов (`UseNumber`), `input_hash` удаляется, остальные поля кодируются с сортировкой ключей, затем считается SHA-256. Дубли ключей и неизвестные поля DTO отвергаются. Выбор общего экзамена для нескольких подразделений и действующей попытки/апелляции выполняют владельцы снимка до передачи в calculate.

Формула первого этапа закреплена в коде:

```text
H = среднее ДЗ типа ОВ с дедлайном в периоде и строго до московской даты as_of
E = среднее уже отобранных экзаменов
T = среднее средних тестов по направлениям
final = (H * 25) / 100 + E * 6 + (T * 45) / 100
```

У ДЗ `status=1` и ненулевой указатель результата означают оценённую работу; сама оценка 0 остаётся завершённой. Остальные включённые работы дают 0 в знаменателе. Отсутствующий результат экзамена и отсутствующая сдача теста дают 0. Учитываемый тест в `queued`, `processing`, `retrying` или `failed` препятствует расчёту; он никогда не превращается в ноль. Tests/exams в переданном входе уже отобраны владельцами по периоду и области. Направления объединяются по Python-совместимому удалению крайних пробелов и Unicode casefold названия; сохраняется первый вариант названия. Пустые компоненты равны 0, вес не перераспределяется, диапазон не ограничивается, промежуточное и итоговое значения не округляются. Порядок float64-операций сохранён. Все числовые значения должны быть конечными.

Полный результат `RatingResult` сохраняется в собственной inbox **до** `POST /internal/ratings/jobs/{job_id}/accounts/{account_id}/result`. Callback содержит ту же область/job/revision/hash/алгоритм, `status=ready`, компоненты, детали и `final_rating`. Ratings сохраняет промежуточные строки и публикует законченную версию; calculate не пишет в его таблицы. Если HTTP-ответ потерян, отправляется тот же сохранённый результат без повторного чтения источников. Отмена, удаление или замена задания дают `skipped`; конфликт другого результата — `failed`.

Временные ошибки повторяются с экспоненциальным интервалом до 32 секунд и случайным разбросом от половины до полного интервала, максимум 8 попыток. Некорректный вход и исчерпание попыток до вычисления сохраняют `status=failed,error_code` и отправляют callback владельцу. Сбой доставки уже готового результата сохраняет этот результат; после исчерпания попыток запись inbox получает `failed` с диагностикой доставки. Если ratings недоступен даже для terminal callback, его восстановление должно вызвать служебный retry ниже или отправить новое сообщение с новым ID и тем же неизменяемым job/account. Повтор исходного message ID сам по себе не снимает терминальный статус inbox.

Служебная диагностика требует `X-Service-Key`:

| Метод | Путь | Результат |
|---|---|---|
| GET | `/internal/calculate/ratings/messages` | Только метаданные; фильтры `job_id`, `account_id`; `limit` 1–100, `offset` 0–100000 |
| GET | `/internal/calculate/ratings/messages/{message_id}` | Неизменный конверт, состояние и сохранённый результат |
| POST | `/internal/calculate/ratings/messages/{message_id}/retry` | JSON `{}`; вернуть `failed`/`retrying` в обработку, сохранив результат |

Unit-проверки рейтинга входят в `go test -race ./...`: формула и пропуски, ОВ/московский дедлайн, равные веса направлений и Unicode casefold, отсутствие округления, pending, конечность чисел, hash/область/ревизия, ACK после записи, повтор callback, исчерпание попыток, отказ редиректа и восстановимые не-JSON ошибки gateway.

После запуска dev:

```sh
cd services/calculate
go test -race ./...
go vet ./...
cd ../..
dev/.venv/bin/python services/calculate/scripts/http_test.py
dev/.venv/bin/python services/calculate/scripts/pool_integration_test.py
dev/.venv/bin/python services/tests/scripts/grading_test.py
dev/.venv/bin/python services/tests/scripts/acceptance_race_test.py
```

Проверки ограничены локальным `cpm_dev`. Unit-тесты проверяют все условия алгоритма и политики, неизменный повтор callback, отсечение чужой области, возобновление страниц и классификацию ошибок, предел/параллелизм пула, независимость новых сдач от заблокированной подготовки пересчёта, штатную отмену и persist-before-ACK параллельных записей. `scripts/pool_integration_test.py` запускает race-проверки реальных Mongo-захватов: 80 заданий, восемь конкурентных исполнителей, 2000 завершённых исторических записей, отсутствие SORT/COLLSCAN, миграция, восстановление lease и отсечение старого владельца. Создаёт и удаляет только новые коллекции `calculate_pool_check_*`; активную inbox не меняет, сервисы не останавливает. Без `CALCULATE_TEST_MONGO_URI` эти opt-in тесты пропускаются обычным `go test`.

HTTP-проверки подтверждают реальные API, Rabbit/Mongo, официальное вычисление, пересчёты, настройки и записи в БД. `scripts/fault_test.py` отдельно проверяет восстановление доставки после временной остановки Mongo; её запускают без параллельных HTTP-проверок, Mongo всегда поднимается обратно.
