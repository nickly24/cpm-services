# Uploads contract — 2026-10-09

## Scope, security and ownership

Public base `/v1/uploads/divisions/{division}`; signed Bearer is checked through existing Auth introspection and Core access on every request. The path division must equal the authenticated selected division, including for organization administrators. Organization/account never come from a browser DTO. Files, sessions, jobs, receipts and events are actor-private in their original organization and division. Cards remain organization-wide, while their import journal still has the original division. Unknown outcomes and retries never follow a newly selected cabinet.

Administrative actions require `upload.view/edit` plus their canonical subject section: `users`, `train`, `tests`, `test-results`, or `exams`. Transform requires Tests edit too. Native Cards UI retains its train gate; additional upload applies only to this coordinator. Student Homework/Attendance links require current owner authorization and are never administrative imports. Protected source downloads recheck the owner. File-registration receipts also recheck current owner access.

## API and idempotency

`GET /catalog`; `POST/GET /sessions`; `GET/PUT /sessions/{id}`; `POST /sessions/{id}/reconcile`; `POST /sessions/{id}/commit`; `GET /jobs`, `/jobs/{id}`, `/jobs/{id}/report`; `POST /jobs/{id}/retry`; `GET /events`; `GET /receipts/{command}`; `POST /files/register`; `GET /files/{id}`, `/files/{id}/download`; `GET /templates/{type}`.

Mutation commands require `Idempotency-Key` of 8–128 ASCII letters/digits/colon/underscore/hyphen; reconcile is a read of uncertain owner state. Persist a key before dispatch. Same key with a different type/target/DTO/source hash returns 409. Native owner command keys are stable UUIDs derived from the coordinator resource and command, satisfying Exams/Core UUID contracts. A receipt describes the HTTP command, not completion of its background import. Confirming an already queued session, even with another command key, returns the same job and binds that receipt to it.

Responses are `{status:true,data:...}` or `{status:false,error:<code>}`. Create returns 201, successful recovery 200, enqueue 202. 401/403 mean current authorization failed, 404 scoped absence, 409 revision/command/outcome conflict, 410 expiration, 413 size limit, 501 unavailable owner adapter, 503 unavailable owner or unknown outcome. Do not automatically invent a new key after an uncertain response.

## Source and previews

Multipart create accepts exactly one `file` and `type`, plus native target fields. Canonical owner filename is `source.<extension>`; the original filename is not retained. Sources are at most 8 MiB, expanded XLSX at most 32 MiB, 2048 archive entries, 64 cells per row, and the type row bound. Formulas, macros, embedded binaries, external relationships and XML entities are rejected. Nothing executes uploaded JavaScript or follows file URLs. Optional OnlineTestPad fields are passed to Tests, which owns their meaning.

Core/Cards/Exams create and edit their own sessions. Create and GET return the complete live preview. After an accepted edit, Uploads reads the complete preview again and checks its owner session/version against the accepted mutation; an intervening change returns 409 while preserving the durable command result. Core legacy-user imports accept at most 100 rows. Exams pages are aggregated completely, at most 5000 rows, with stable session/revision/state/total, offsets and validation fingerprint; all page-local errors are aggregated too. A partial or changed preview fails explicitly.

Tests JSON/OnlineTestPad and external-result previews use its protected stateless validation endpoints with the current bearer and existing service key. Uploads stores the scoped canonical input and exact validation snapshot, hashes and target revision in its own preview table. This stores no new Tests business object. Reads and confirmation revalidate current owner rights and the whole preview fingerprint. External matching and grades remain Tests business rules; Uploads parses source rows and preserves their physical row numbers and raw percentage values. Source input is at most 8 MiB; the normalized Tests DTO is at most 1 MiB. The external test target stays fixed throughout the session.

External XLSX optionally accepts the exact ASCII headers `account_id` and `legacy_student_id` (case-insensitive). They identify distinct Auth accounts and Core student profiles. Blank cells omit the field; supplied values must be positive decimal int64. Text cells preserve all digits up to int64 maximum; numeric cells above 2^53−1 require text to avoid spreadsheet rounding. Invalid cells and duplicate ID headers return 422 with the physical row and field. The legacy generic `id` column remains a source number. Tests owns scoped ID lookup and consistency: supplied IDs disable name matching, and conflicting account/profile IDs produce an invalid preview rather than a fallback to another pupil.

Generic preview redaction and report assembly preserve JSON integer digits and number lexemes instead of decoding through float64. Native account/profile fields remain JSON integers. A JavaScript client must reject unsafe numeric edits or decode these fields losslessly; it must not re-submit a rounded identifier from a preview.

Credential source bytes are processed in memory and never persisted. Core stores hashes and does not expose passwords. Uploads masks sensitive response keys and has no credential export. Other sources and Tests snapshots expire after 72 hours. Expired queued/retry/awaiting-authorization jobs become `failed/source_expired`; maintenance removes their source bytes and snapshots, excluding a running job. Retention never deletes owner data or S3 objects. An expired input cannot be retried into a fresh import.

Core credential preview recovery uses its protected receipt and then GET of the owner session. A missing receipt does not prove that parsing did not occur, so credentials are not silently resent. Cards/Exams can recover uncertain create by repeating the identical native command under their verified idempotency contract. Editing freezes the coordinator while the owner runs. Uncertain edits become `edit_unknown`; reconciliation checks the live owner revision and uses a conditional update. An in-flight `editing` session cannot be reconciled prematurely.

After owner create responds or fails, only the coordinator SQL outcome/receipt/event persistence can outlive browser cancellation, synchronously for at most five seconds. Owner HTTP always uses the original request context and live bearer. Credential GET/reconcile finds the unique original scoped `session.create` receipt and reads the exact native creation receipt without resending bytes or creating a new key. A missing native receipt leaves a young staging request active; staging older than 180 seconds becomes `outcome_unknown`. Missing or ambiguous coordinator metadata fails closed. Conditional updates prevent late errors or recovery responses from reopening a queued/completed session. A found native receipt must resolve to the same positive numeric Core session and complete protected preview.

## Protected templates

Each catalog item has a `template` boolean. `cards.transform`, Homework and Attendance have no file template and return `400/template_not_applicable`. Other templates require current upload and subject permissions. Core legacy additionally requires edit rights, matching its native template contract; its catalog flag is disabled for a read-only actor.

`users.credentials` returns a header-only CSV. Core owns the five-column legacy XLSX; Cards and Exams own their XLSX formats. Exams requires a positive `target_id`. `tests.json` requires a positive `direction_id` and accepts `format=cpm_json` (default, .json) or `format=online_test_pad` (.js with a literal JSON object). `tests.external-results` requires its 24-hex `target_id` and returns the owner's eight-column XLSX. Templates contain synthetic examples; no pupil results or generated credentials are exported.

Uploads forwards only the current bearer to fixed owner routes. Unknown or repeated query parameters fail before dispatch. Downloads retain exact owner bytes after bounded file/MIME/UTF-8 validation, use controlled filenames and media types, and never forward owner cookies or redirects. JSON and JavaScript templates use `application/json` and `text/javascript`; JavaScript is inspected without execution. All responses are private, no-store and nosniff.

## Delivery and current execution dependency

Confirm `{expected_revision:<n>}` freezes the preview and creates one job per session. The same SQL transaction writes the scoped Rabbit outbox command. Rabbit quorum execute/retry/dead queues, publisher confirms, inbox deduplication, generations and leases handle delivery and recovery. SQL maintenance only repairs uncertain metadata and delivery proofs; it never selects and directly executes an import. Messages carry IDs, source hash and revisions, without bearer, passwords, personal rows or file bytes. Detailed topology and actual transport evidence: [rabbit-delivery.md](rabbit-delivery.md).

Human consent for scoped background authorization was received and directly verified. The current source implements frozen Auth protocol revision 2 and the [confirmed public API](background-public-api.md): `{expected_revision,confirmed:true}`, immutable command reservation before readonly native preparation/issuance, atomic grant binding/outbox, current owner authorization, and receipt-verified completion. No bearer is retained in SQL, Rabbit or background memory. The feature is disabled by default; unchanged historical runtime still reports `awaiting_authorization/background_authorization_pending`, zero progress and no final report. Source implementation does not establish real Auth/Rabbit/UI deployment readiness. A marker saved before possible apply makes subsequent work receipt-only; expiry, missing receipt, denied current rights or response loss never imply no changes. Explicit recovery cannot issue a second apply. Historical technical jobs are not silently authorized.

The eventual application must verify the original actor's current permissions and exact operation scope, and let the subject owner atomically validate/apply the frozen input with a stable receipt. Service keys alone cannot supply actor authorization. No distributed exactly-once guarantee is claimed.

## Homework and Attendance references

`POST /files/register` with `{type:"homework.pdf",owner_reference:"<owner job UUID>"}` checks the student's existing Homework job. This copies no PDF/S3 key and adds no upload/complete/retry/cancel/submit/review wrappers. Download directs the caller to the owner's protected submission file URL. Homework, File-work and S3 retain their existing lifecycle and queues.

Attendance registration uses `{type:"attendance.zap-images",target_id:"<zap>",owner_reference:"<1-based index>"}`. The owner metadata envelope is unwrapped through `data.value`; image_count controls index existence. Protected metadata, exact receipt recovery and binary download recheck live owner access. Only PNG/JPEG is accepted; creating/deleting an attachment stays in Attendance. The current cabinet must match the registry division; change context before registering another accessible division. Registry expiry affects the reference only.
