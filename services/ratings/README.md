# Ratings

Результаты сквозных проверок и команды повторного запуска: [testing.md](testing.md).

Финальная передача рабочего dev-сервиса с контрактами, миграциями, образами и фактическими проверками: [handoff 9 октября 2026](docs/handoff-2026-10-09.md).

Go-сервис формирует рейтинги отдельно для `organization_id + division_id`. У одного `account_id` в двух подразделениях две независимые строки рейтинга. Ratings принимает запросы, собирает входы через API владельцев, сохраняет задания и персональные снимки, отправляет их через RabbitMQ в calculate, принимает результаты и публикует законченную версию. Математика находится в calculate. Ratings пишет только свои таблицы MySQL; чужие БД не являются межсервисным API.

По умолчанию HTTP слушает `127.0.0.1:8012`. Машинный контракт доступен в `GET /openapi.json`; лимит JSON-тела запроса — 4 MiB, сохранённого персонального входа calculate — 2 MiB.

## Задание и публикация

1. Администратор передаёт период и `Idempotency-Key`. В одной транзакции сохраняются задание и новая ревизия области. Тот же ключ с тем же периодом возвращает исходное задание; другой период с тем же ключом даёт `409 idempotency_conflict`. Для одного подразделения одновременно активно одно задание; конкурентный запрос получает `409 rating_job_active`.
2. Ratings получает снимки core, homework, tests и exams. Организация, подразделение, период и UTC `as_of` фиксированы в задании. Входы каждого ученика и outbox сохраняются вместе. Источник тестов с незавершённой проверкой переводит задание в ожидание; pending не заменяется нулём.
3. Каждому ученику соответствует собственное сообщение `ratings.calculate.requested` в маршруте `ratings.calculate.requested.v1` exchange `cpm.events`. Calculate читает сохранённый персональный вход и асинхронно возвращает результат. Число обработанных учеников увеличивается по мере принятия результатов.
4. До первого сохранения **результата** ученика вызывается `POST /internal/core/rating-locks` с `{account_id,division_id}`. Успешная постоянная метка защищает участие от удаления, включая нулевой рейтинг. Снимок исходных данных до вычисления ещё не является сохранённым результатом рейтинга.
5. Готовые строки остаются в staging. Публикация одной транзакцией проверяет ревизию, активное задание, lease и точное число готовых результатов, затем меняет `published_job_id` своей области. Во время расчёта пользователи продолжают читать предыдущую опубликованную версию. Частично рассчитанный список не выдаётся как опубликованный рейтинг.

Собственные таблицы определены в [migrations/001_ratings.sql](migrations/001_ratings.sql): `ratings_scopes_v1`, `ratings_jobs_v1`, `ratings_items_v1`, `ratings_outbox_v1`. История опубликованных заданий и их персональные результаты сохраняются. Состояние задания и outbox долговечны; захват задания использует MySQL lease на 90 секунд, heartbeat каждые 20 секунд и `SKIP LOCKED`. Публикация и callback дополнительно проверяют состояние под блокировками, поэтому поздний результат отменённого или заменённого задания не может заменить более новую версию.

Надёжная доставка не означает общую транзакцию между сервисами. Снимки разных владельцев читаются независимо; сравнение их хешей обнаруживает изменённые входы. Между последней удалённой проверкой и локальной публикацией остаётся распределённая гонка. API актуальности сообщает изменение источника или недоступность проверки, а не обещает мгновенную глобальную согласованность.


Новые расчёты включают только учеников с `is_active=true` из scoped Core roster. Отбор выполняется в `Store.Prepare` до формирования персональных входов, outbox и `total_count`; неактивные ученики, в том числе с незавершёнными оценками, не создают персональные задания Calculate. Полный исходный снимок Core и его hash сохраняются без изменений для проверки актуальности. Пустой состав активных учеников — допустимая новая публикация с нулём строк.

Отключение аккаунта не переписывает уже опубликованные рейтинги, оценки или учебную историю. После нового завершённого расчёта текущий указатель показывает версию без неактивного ученика; прежняя версия доступна по `version`. Повторная активация возвращает ученика в следующий новый расчёт. Сырой Core roster сохраняет неактивных участников для прежних проверок доступа проктора к историческим публикациям; фильтрация опубликованных строк по текущей активности не применяется.

## Формула первого этапа

`algorithm_version = legacy-rating-v1`. Формула закреплена в calculate и сохраняет порядок операций старого Python-кода:

```text
H = среднее включённых домашних работ
E = среднее включённых экзаменов
T = среднее средних тестов по направлениям
final = (H * 25) / 100 + E * 6 + (T * 45) / 100
```

В H входят только ДЗ с точным названием типа `ОВ`, дедлайном внутри включительного периода и строго до московской календарной даты `as_of`. Только `status=1` с присутствующим результатом даёт сохранённую оценку; остальные включённые работы дают 0 и остаются в знаменателе. Завершённая работа с оценкой 0 остаётся завершённой. Штраф за опоздание уже входит в оценку homework и заново не начисляется.

В E каждый отобранный экзамен имеет одинаковый вес. Отсутствующий результат даёт 0. Exams выбирает действующую завершённую попытку и применённую апелляцию до выдачи снимка; ratings/calculate не пересчитывают голоса комиссии, пороги или попытки. Общий экзамен нескольких подразделений включается в снимок каждого соответствующего подразделения, а результаты остаются в области запрошенного подразделения.

В T каждый включённый тест входит в среднее своего направления; направления затем имеют равные веса. Группировка использует крайние пробелы и Unicode casefold названия, сохраняя первый вариант названия. Отсутствующая сдача даёт 0; `queued`, `processing`, `retrying`, `failed` или готовый результат без балла препятствуют публикации. Пустые компоненты равны 0. Вес не перераспределяется, диапазон не ограничивается, промежуточное и итоговое значения не округляются. Все числовые оценки должны быть конечными.

## Источники и подключение exams

Внутренние вызовы выполняются с `X-Service-Key`:

| Владелец | Метод и путь | Входы |
|---|---|---|
| Core | `POST /internal/core/ratings/snapshot` | Участники выбранного подразделения, профили и направления |
| Homework | `POST /internal/homework/ratings/snapshot` | Задания и сохранённые оценки участников |
| Tests | `POST /internal/tests/ratings/snapshot` | Опубликованные активные тесты периода и официальные результаты в подразделении |
| Exams | `GET /internal/exams/rating-snapshot` | Отобранные экзамены, действующие результаты, попытки и апелляции |

Core/homework/tests принимают POST `{organization_id,division_id,date_from,date_to,as_of}`. Exams принимает GET query `organization_id`, `division_ids` с одним запрошенным подразделением, `date_from`, `date_to`, `as_of`; его ответ содержит `source_revisions` и `snapshot`. Ответы обёрнуты в `{status:true,data:...}`. Адаптер ratings преобразует выбранные exams оценки в свой `ExamsSnapshot`, сохраняя идентичность экзамена и подразделения, и вычисляет устойчивый хеш из ревизий и содержимого. HTTP-вызовы не пересылают служебный ключ при редиректах.

Адаптер реализован по текущему Go-контракту exams и описан в [docs/exams-snapshot-contract.md](docs/exams-snapshot-contract.md). Сам Go-сервис exams уже существует в проекте; его фактическое подключение и эксплуатационная готовность проверяются отдельно. Каталог снимка exams передаёт необязательное `exam_name`; адаптер сохраняет название в деталях рейтинга. Для старого или пустого поля остаётся стабильное `Экзамен <ID>`. Переименование меняет ревизию и хеш снимка, при этом опубликованная историческая версия сохраняет прежнее название. Внешний источник реализован владельцем Go tests и описан в [docs/external-tests-snapshot-contract.md](docs/external-tests-snapshot-contract.md): подразделение получает только подключённые внешние тесты периода и свои результаты. Legacy MySQL и production для этого источника не читаются. Исчезновение обязательного источника не является основанием объявлять его нулём.

`RATINGS_EXAMS_MODE=required` — значение по умолчанию. В этом режиме отсутствие `RATINGS_EXAMS_URL` блокирует подготовку с диагностикой `exams_not_connected`; недоступный источник даёт ошибку/ожидание, а не пустой экзаменационный компонент.

`RATINGS_EXAMS_MODE=dev_empty` явно подставляет пустой экзаменационный снимок для интеграционной проверки dev. Конфигурация разрешает этот режим только при `MYSQL_DATABASE=cpm_dev`; режим присутствует в health и актуальности рейтинга. Результаты такого режима имеют экзаменационный компонент 0 и не являются подтверждением полного рейтинга с реальными экзаменами.

`RATINGS_EXTERNAL_TESTS_MODE=required` — значение по умолчанию. Tests должен вернуть scoped `external_domain:{schema_version:1,status:"ready",organization_id,division_id}`, явный массив `external_tests`, включая корректный пустой `[]`, и 64-символьную hex-версию `external_source_version`. Отсутствующий массив оставляет задание в ожидании `external_tests_not_connected`; пропущенная версия или неполные строки отклоняются. Режим `dev_internal_only` оставлен только для совместимости с прежними локальными проверками `cpm_dev` и обозначается в снимке/health/freshness; он не доказывает полноценное подключение внешних результатов.

## HTTP и права

Каждый публичный запрос проверяет Bearer через auth introspection. `organization_id` берётся из проверенного auth-контекста, подразделение — из пути и проверки core. Организацию или аккаунт нельзя подменить в теле запроса.

| Метод | Путь относительно `/v1/ratings/divisions/{division}` | Действие |
|---|---|---|
| POST | `/jobs` | Создать задание: `{date_from,date_to}`, обязательный `Idempotency-Key` |
| GET | `/jobs`, `/jobs/{job}` | История заданий и стадия/счётчики выбранного задания |
| POST | `/jobs/{job}/cancel` | JSON `{}`; отменить ещё не опубликованное задание |
| POST | `/jobs/{job}/retry` | JSON `{}` и новый ключ; создать новое задание того же периода |
| GET | `/ratings` | Опубликованный список, поиск `q`, `limit` 1–200, `offset` 0–100000 |
| GET | `/me` | Собственный рейтинг ученика; до публикации `rating:null` |
| GET | `/accounts/{account}` | Доступная детализация ученика |
| GET | `/versions` | До 100 опубликованных версий по убыванию ревизии |
| GET | `/report` | Полный JSON-отчёт с периодом и деталями для экспорта клиентом |

Для чтения опубликованной версии список/детализация/отчёт поддерживают `version=<job UUID>`; иначе используется текущий указатель. Чужая организация или подразделение не открываются этим параметром. До первой публикации отчёт возвращает `period:null` и пустой список учеников. Endpoint отчёта не создаёт XLSX-файл: форматирование экспорта выполняет клиент.

Полный администратор работает внутри своей организации. `staff_admin` требует право `ratings.view`, а создание/отмена/повтор — дополнительно `ratings.edit`, в разрешённом подразделении. Supervisor может читать задания, версии и отчёт. Ученик видит только собственную строку; проктор видит только участников своей группы и не получает административный журнал. Фильтрация доступа применяется до поиска и подсчёта выдаваемого количества.

Место — порядковая позиция всей опубликованной версии подразделения **до** поиска, пагинации и фильтрации по пользователю/группе. Сортировка: итоговый балл по убыванию, затем полное имя и `account_id`. Равные баллы получают отдельные последовательные места. Это отличается от исторического отображения `index+1` после поискового фильтра во фронтенде монолита.

Для calculate:

| Метод | Путь | Действие |
|---|---|---|
| GET | `/internal/ratings/jobs/{job}/accounts/{account}/input` | Неизменяемый персональный вход |
| POST | `/internal/ratings/jobs/{job}/accounts/{account}/result` | Готовый результат либо `{status:"failed",error_code,...метаданные}` |

Эти методы требуют `X-Service-Key`. Область, job, ревизия, аккаунт, алгоритм и input hash callback должны совпадать с сохранённым входом. Идентичный повтор результата безопасен; другой результат для уже сохранённой строки возвращает `409 result_idempotency_conflict`. Отменённые/заменённые задания возвращают `409 stale_rating_job`. Готовое задание остаётся доступным для идемпотентного повтора callback.

## Диагностика и восстановление

Стадии: `preparing`, `waiting_sources`, `queued`, `running`, `validating`, затем `completed`, `failed`, `cancelled` или `superseded`. Frontend опрашивает `/jobs/{job}` и показывает `total_count`, `processed_count`, `error_code`; прогресс означает принятые персональные результаты, не частичную публикацию.

`tests_calculation_pending`, `exams_not_connected`, `external_tests_not_connected` и `rating_source_changed` при подготовке сохраняют ожидание источников с повтором каждые 5 секунд; это ожидание не исчерпывает бюджет временных сетевых ошибок. Для сетевых/хранилищных сбоев предусмотрено до 8 попыток с задержкой. Незавершённое вычисление персональных результатов ограничено 30 минутами с момента создания задания, затем `failed/calculation_timeout`. Если входы изменились перед публикацией, задание становится `superseded/source_changed_before_publication`; нужен явный retry с новой ревизией.

Ответы используют `{status:true,data:...}` либо `{status:false,error:<код>}`. `400` означает некорректный DTO/период/ключ; `401` — авторизацию; `403` — недостаточные права; `404` — отсутствующий или недоступный объект; `409` — конфликт задания, ревизии, ключа или результата; `503` — временно недоступные зависимости/хранилище. Новый запрос принимается с `202`; идемпотентное возвращение существующего задания — `200`.

`freshness` сообщает `never_calculated`, `source_snapshot_invalid`, `source_unavailable`, `source_changed` или `calendar_transition`; пустая причина означает отсутствие выявленного изменения. При сбое источника прежний опубликованный рейтинг сохраняется с диагностикой актуальности. Проверка актуальности читает API владельцев, поэтому недоступность источника не означает нулевой рейтинг. Постоянный consumer `exams.source.changed` дополнительно сохраняет scoped watermark, отмечает устаревшую публикацию и блокирует публикацию снимка с более старой версией. Он не создаёт автоматических jobs; контракт и миграция описаны в [docs/source-events.md](docs/source-events.md).

После рестарта сохранённые незавершённые задания снова захватываются после истечения lease. Calculate также хранит собственный lease и результат перед callback. После восьми неудачных попыток доставки его сохранённый результат требует служебного retry `/internal/calculate/ratings/messages/{message_id}/retry` или нового message ID с тем же неизменяемым заданием. Простое повторение исходного message ID сохраняет идемпотентность, но не снимает терминальный статус calculate inbox.

Публичный retry ratings создаёт новую ревизию и заново собирает входы; он не меняет старую опубликованную версию. Отмена не удаляет предыдущую публикацию и постоянные метки истории в core. API архивирования/удаления опубликованной истории в этом этапе отсутствует.

## Конфигурация и проверка

Нужны `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD`, `AUTH_INTERNAL_KEY` длиной минимум 32 символа, `RABBITMQ_URL`, `RATINGS_AUTH_URL`, `RATINGS_CORE_URL`, `RATINGS_HOMEWORK_URL`, `RATINGS_TESTS_URL`, `RATINGS_CALCULATE_URL`. Опциональны `MYSQL_TLS`, `RATINGS_LISTEN_ADDR`, `RATINGS_EXAMS_URL`; `RATINGS_EXAMS_MODE` и `RATINGS_EXTERNAL_TESTS_MODE` по умолчанию `required`. Внешние HTTP-зависимости используют HTTPS; HTTP разрешён для соответствующих Compose-имён, localhost и 127.0.0.1. Для exams в `cpm_dev` также разрешён `host.docker.internal`, чтобы подключаться из контейнера к соседнему локальному dev-процессу. Внешний RabbitMQ использует AMQPS. Секреты задаются конфигурацией окружения и не входят в документацию или события.

`GET /health/live` проверяет процесс. `GET /health/ready` отражает готовность хранилища и режим exams; он не является доказательством завершённого расчёта с реальными источниками.

```sh
cd services/ratings
go test -race ./...
go vet ./...
```

Для локального dev из корня проекта предусмотрены `./dev/ratings prepare` и `./dev/ratings offline-integration-up`; второй вариант собирает Go-бинарники на хосте и запускает интеграционный Compose с владельцами снимков/calculate. Режимы `dev_empty` и `dev_internal_only` допустимы лишь как явно обозначенные неполные локальные проверки. После сквозной проверки живых владельцев снимков dev переключается на `required`; готовность подтверждается реальным расчётом, а не отключением обязательных источников.

Проверки не должны подключаться к production. Отдельная интеграционная проверка требует локального dev, синтетических данных и запущенных владельцев снимков/calculate. Гарантия нагрузки для 450 одновременно сдающих тесты требует отдельного совместного измерения и не следует из прохождения unit-тестов.

Отдельный HTTP-сценарий `scripts/tenant_test.py --allow-fixtures` проверяет две dev-организации, четыре новых подразделения, отзыв прав действующего токена, несколько участий, чужие ID заданий/версий/аккаунтов, JSON-отчёт для экспорта и область callback. Он требует реальные exams и внешний источник tests в режиме `required`; все данные создаются через public API, без доступа к базам и управления очередями. Предусловия, ожидаемые результаты и закрытые отчёты описаны в [docs/tenant-acceptance.md](docs/tenant-acceptance.md).

На сохранённых tenant fixtures отдельный HTTP-прогон проверяет включительные периоды, будущие ОВ, нулевые/неизвестные внешние результаты, ревизии источников и неизменность истории: [docs/period-source-acceptance.md](docs/period-source-acceptance.md). Фактический результат — 846 проверок, 23 завершённых задания и 46 персональных входов/результатов; изменения источников A1 сохранили свежесть остальных трёх областей.

Математический паритет дробных оценок с наблюдаемым dev CPython3.12.14 проверен четырьмя IEEE-754 golden-векторами настоящих legacy-функций. Описаны [контроль суммирования и промежуточного округления](../calculate/docs/ratings-legacy-golden.md). Новые детали тестов сохраняют `calculation_status:ready|missing`, поэтому завершённый ноль отличим от отсутствующего результата; старые cached детали без этого поля остаются читаемыми.

## Быстрый административный список

`GET /v1/ratings/divisions/{division}/table?limit=50&offset=0&q=...&version=...` отдаёт SQL-страницу сохранённых итогов без деталей работ и без ожидания владельцев источников. `publication` содержит version_id/revision/as_of/период, до первой публикации null. Порядок: итог по убыванию, бинарный порядок полного имени, account_id. Место вычисляется по всей версии до поиска; поиск охватывает имя, группу, класс и account_id. Следующие страницы привязаны к version_id первой страницы. Указатель, версия, count и страница читаются в одном read-only REPEATABLE READ snapshot. Доступ: ratings.view либо supervisor; student/proctor используют прежние ограниченные endpoints.

`GET .../freshness?version=<version_id>` отдельно проверяет живые источники по прежнему контракту. Пока проверка выполняется, клиент обозначает её ожидание, но уже показывает сохранённые строки. Ошибка проверки не очищает таблицу и не объявляет её актуальной. Auth/tenant/permission fence, callback validation, перерасчёт, формула, полный report и detail остаются прежними.
