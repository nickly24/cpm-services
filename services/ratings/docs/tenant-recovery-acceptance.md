# Отмена, публичный повтор и реальный crash ratings

`scripts/tenant_recovery_test.py` использует только сохранённое собственное B2 из успешного tenant-запуска. Для `10d3deb9e73c` это подразделение `10191` организации `2001`, два собственных синтетических ученика. Школы, направления, тесты, экзамены, оценки и настройки источников не создаются и не меняются. Первоначальный tenant manifest не перезаписывается.

## Окно и ограничения

Запуск требует отдельного согласованного окна с root после завершения других сценариев. Во время окна нельзя создавать рейтинговые задания в иных областях, менять источники B2 или справочник направлений организации `2001`. Сервис ratings кратко становится недоступным всем клиентам; calculate, RabbitMQ, владельцы источников и базы продолжают работать.

Проверяются закрытые настройки фиксированного `cpm_dev`, все loopback health API и оба режима `required`. HTTP-перенаправления запрещены. Два аккаунта сверяются одновременно по точным ID, логинам, роли `student`, участию B2 и префиксу сохранённого запуска; подразделение — по точному названию и активной организации. Проверка запускается с действующей полной ролью `dev_admin_math` в B2.

Перед началом и непосредственно перед crash проверяется отсутствие конкурирующих активных рейтинговых заданий. Docker-цель ограничена `cpm-dev-ratings-1`, точными Compose labels `project=cpm-dev`, `service=ratings` и работающим контейнером. Единственные команды изменения состояния процесса — `docker kill` и `docker start` этого контейнера, без пересборки, Compose down или удаления volumes.

SQL читает данные и берёт `SELECT ... FOR UPDATE` только двух собственных строк `auth_users` внутри отдельной транзакции. Эти блокировки задерживают обязательный Core history-lock при callback, сохраняя исходные строки. Транзакция откатывается и закрывается, включая `finally`. SQL UPDATE/INSERT/DELETE, искусственное истечение lease, прямые изменения Mongo и управление очередями отсутствуют. Mongo только читает собственные документы calculate inbox.

Вспомогательный процесс без credentials через 60 секунд может запустить только тот же первоначально проверенный контейнер с тем же Docker ID и labels, если основной процесс неожиданно завершился после остановки ratings. При штатном восстановлении этот watchdog снимается. `finally` также освобождает собственные блокировки и восстанавливает ratings при ошибке.

## Проверка

1. Сохранить текущую полную публикацию B2 и её результаты. История может быть помечена `source_changed` из-за согласованного добавления пустого направления; это не изменяет прежние оценки.
2. Удержать два собственных аккаунта и создать задание. Дождаться обеих подтверждённых команд и двух сохранённых outputs calculate при нулевом принятом progress; старая публикация остаётся текущей.
3. Отменить задание публичным `/jobs/{job}/cancel`, освободить блокировки, проверить поздний cached callback: точный `409 stale_rating_job`. Настоящий worker завершает обе доставки как `skipped/rating_job_cancelled_or_superseded`, не увеличивая progress.
4. Вызвать публичный `/jobs/{cancelled}/retry` с новым ключом. Повтор того же запроса возвращает тот же новый job. Новая ревизия полностью публикуется, остаётся свежей и содержит прежние бизнес-результаты; исходная история сохраняется, отменённое задание отсутствует в `/versions`.
5. Создать отдельное третье задание с вновь удержанными callback. После durable outputs остановить только ratings, освободить блокировки и увидеть настоящие retry calculate с теми же сохранёнными bytes. Запустить только ratings.
6. Дождаться возобновления и завершения исходного третьего задания. Если процесс сохранил действующий lease, его срок истекает естественно; время и записи lease не подменяются. Сравнить source hash, snapshot hash, каждый неизменяемый input и byte-identical cached output; ID сообщений, аккаунты и ревизия не заменяются. Публикация атомарно переключается, обе предыдущие завершённые версии остаются в истории.

## Команда и отчёт

Выполнять только после отдельного подтверждения окна root:

```sh
dev/.venv/bin/python services/ratings/scripts/tenant_recovery_test.py \
  --fixture-run-id 10d3deb9e73c --allow-ratings-restart
```

`--help` и синтаксическая проверка не обращаются к runtime. Ожидаемая длительность живого сценария — около 2–3 минут, в основном естественное ожидание lease; остановка ratings обычно занимает несколько секунд, watchdog ограничен 60 секундами.

Отчёт пишется отдельно в `dev/local/ratings-tenant-recovery-report.json` с режимом `0600`. Закрытый manifest каждого собственного recovery-запуска содержит ID трёх заданий, ключи повторов, исходную версию и период; токены, пароли и исходные outputs туда не входят. История, ratings locks и фикстуры сохраняются. Старый `ratings-recovery-report.json` не перезаписывается. Успешный живой результат подтверждается только новым отчётом `status=passed`.
