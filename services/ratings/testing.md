Основной сценарий проверяет формулу, отсутствующие оценки и настоящие нули, сохранение outbox/inbox, конкурентную идемпотентность, повтор callback, ревизии, права, отдельные подразделения, постоянные метки core, историю и актуальность. Незавершённая проверка теста оставляет задание в `waiting_sources`: предыдущая версия остаётся доступной. Отмена не публикует поздний результат.

В аварийном сценарии сохранены персональные входы и вычисленные результаты calculate, затем процесс ratings принудительно завершён до принятия callback. Calculate сохраняет точные вычисленные результаты при недоступном callback. После запуска ratings то же задание публикуется; хеши исходных снимков и входов, идентификаторы сообщений и сохранённые результаты остаются прежними. Искусственное истечение lease не использовалось. Перезапускались только ratings.

В экзаменационном сценарии общий экзамен имеет один ID и оценки 4 и 2 одного ученика в разных подразделениях. Независимая копия получает новый ID, сначала не содержит сдач, затем получает собственную оценку 5. Средние E равны 4 и 3.5; итоговые рейтинги равны 84 и 21. Домашние работы и тесты сохраняют предыдущие значения. Отсутствующий результат другого ученика остаётся нулём в знаменателе. Повторная проверка актуальности возвращает свежий рейтинг.

Unit-тесты также покрывают точный порядок операций исходной формулы, Unicode casefold, московские календарные границы, большие ID и канонический хеш, неоднозначный JSON, отсутствие обязательного источника, неполную публикацию, смену группы проктора и защиту новых ревизий.

Новый BFF-сценарий `bff_integration_test.py` создаёт все источники через публичные API, а ratings вызывает с отдельными сессионными cookie BFF. Он не вызывает временную Mongo-подмену и SQL-проверки прежнего `http_test.py`. Реальное сообщение `ratings.calculate.requested.v1` проверяется собственной временной очередью Rabbit: две устойчивые доставки совпадают по идентификаторам и хешам с готовым durable inbox calculate. Очередь удалена после проверки; чужие очереди и данные не изменялись.

На данных запуска `2c8415e2159e` компоненты H=40 и T=25. Пока пересдача не завершена, действует первая апелляция 4 и внешний экзамен 2: E=3, итог 39.25. Пересдача с нулём заменяет первый результат: E=1, итог 27.25. Общий внешний экзамен с оценкой 5 в другом подразделении и независимая копия без сдачи дают E=2.5, итог 15. Историческая первая версия сохраняет 39.25; второй ученик имеет настоящий опубликованный ноль и место 2. Проверены личная видимость студента, актуальная группа проктора, supervisor, staff view/edit, разделение подразделений и организаций, фильтрация с сохранением общего места, отмена, повтор, идемпотентность и постоянные метки участия для ненулевых и нулевых рейтингов.

Исправлены чтение явной версии до первой публикации и ошибочное превращение сбоя базы в пустой рейтинг. Optional `exam_name` владельца проходит в детали calculate; unit-тесты проверяют старый fallback и смену хешей при переименовании без изменения сохранённой истории. `go test -race ./...` и `go vet ./...` прошли во всех шести модулях ratings, calculate, core, homework, tests и exams.

## Повторный запуск

```sh
./dev/ratings prepare
./dev/ratings offline-integration-up
dev/.venv/bin/python services/ratings/scripts/http_test.py
dev/.venv/bin/python services/ratings/scripts/recovery_test.py --allow-ratings-restart
```

HTTP-сценарий создаёт собственные новые области. Для сценария экзаменов нужны работающий Go exams и `RATINGS_EXAMS_MODE=required` с его доступным URL. Он использует области предыдущего HTTP-сценария и требует отсутствие посторонних экзаменов в этих областях. Передайте точный `run_id` из нового отчёта:

```sh
dev/.venv/bin/python services/ratings/scripts/exams_test.py --fixture-run-id <run_id>
```

Пересобрать только ratings, сохранив остальные контейнеры, позволяет `./dev/ratings offline-ratings-up`. Миграции применяются по порядку из `migrations/`; вторая миграция делает ключи идемпотентности чувствительными к регистру.

Новый сценарий требует работающие BFF `8001` и Go exams `8010` в текущем `cpm_dev`. Он создаёт новый отдельный набор публичных фикстур; опубликованные метки участия сохраняются:

```sh
dev/.venv/bin/python services/ratings/scripts/bff_integration_test.py
dev/.venv/bin/python services/ratings/scripts/bff_waiting_fixture.py prepare
```

`bff_waiting_fixture.py prepare` создаёт дополнительное подразделение с опубликованным нулём и открытой официальной попыткой. Команда `finalize` предназначена только для заранее согласованной короткой остановки calculate с гарантированным восстановлением: она отправляет реальный неправильный ответ через public tests API и проверяет `queued` без оценки. Сам скрипт не останавливает процессы и не обращается к базам.

В отдельном подразделении `10115` root приостановил только calculate на 43.3 секунды; страховочный watchdog гарантировал возобновление через 60 секунд. Процесс не перезапускался. Реальный public finalize дал `queued` без результата, рейтинговое задание стало `waiting_sources/tests_calculation_pending`, UI сохранил предыдущую опубликованную нулевую версию, отменил задание и создал повтор с новым ID и большей ревизией. После возобновления официальный тест получил `ready` и оценку 0; повтор полностью опубликовался для одного участника. Отдельный read-only `bff_waiting_fixture.py verify` подтвердил готовый inbox calculate, сохранение первоначальной версии и отсутствие отменённого задания в истории публикаций. Проверки не меняли источники основных подразделений `10110` и `10111`.

Несекретные отчёты нового сценария находятся в `dev/local/bff-ratings-http-report.json`, `bff-ratings-waiting-prepare-report.json`, `bff-ratings-waiting-finalize-report.json`, `bff-ratings-waiting-verify-report.json`; manifest для браузеров — `bff-ratings-demo.json`. Пароли и токены туда не записываются.

Локальные отчёты находятся в `dev/local/ratings-http-report.json`, `ratings-recovery-report.json`, `ratings-exams-report.json` и `ratings-case-keys-report.json`. Приватные manifests фикстур содержат credentials и не должны публиковаться.

## Граница проверки

Перечисленные выше исторические отчёты получены с настоящим API экзаменов в режиме `required` и явно обозначенным `RATINGS_EXTERNAL_TESTS_MODE=dev_internal_only`. Go tests теперь реализует отдельный внешний источник с массивом `external_tests`, версией `external_source_version`, ревизиями каталога и результатов; unit/Mongo HTTP checks и Go race/vet проверяют этот контракт. Переключение живого dev на полный `required` выполняется после отдельной сквозной проверки внешнего домена. Отсутствующий массив, версия или недоступный владелец не становятся нулевым компонентом.

Проверки подтверждают рабочую цепочку и восстановление на этих данных. Они не являются нагрузочным измерением на 450 одновременно сдающих учеников или проверкой production-развёртывания. Согласованность снимков между сервисами проверяется хешами, без общей распределённой транзакции.
