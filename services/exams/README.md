# Exams service

Сервис экзаменов на Go: банк организации, общий экзамен для нескольких подразделений, глубокое копирование, устное проведение, внешний результат, подготовка и исходные данные для будущего рейтинга.

## Границы данных

`organization_id`, выбранное подразделение и права получаются только из действующей сессии auth. Произвольные заголовки и параметры клиента не выбирают область доступа. Идентификатор ученика/экзаменатора — **auth account_id**, не ID профиля монолита.

Один общий экзамен имеет один ID, название, направление, части и банк вопросов. Подключение к подразделению создаёт собственные настройки, окно проведения, комиссии, назначения, льготы, попытки, результаты и подготовку. Результат ученика в подразделении A не засчитывается в B, даже если ученик и экзамен общие. Первое подразделение является владельцем общего содержимого. Администратор организации управляет всеми подключениями; сотрудник меняет общее содержимое только в контексте владельца и при наличии доступа ко всем подключённым подразделениям. Сотрудник может прочитать общее содержимое экзамена в банке организации и скопировать его в выбранное подразделение, имея exams.edit.

Глубокая копия получает новый ID и независимые название, направление, части, вопросы и настройки выбранного подразделения (для экзамена из банка — владельца). Она сохраняет `origin_exam_id` для происхождения. Комиссии, назначения, льготы, попытки, голоса, результаты, история апелляций и прогресс учеников не переносятся. Подключение общего экзамена создаёт пустую операционную область; для внешнего экзамена переносится исходная дата. Затем настройки подразделений редактируются независимо.

Таблицы `exams_*_v1` принадлежат этому сервису. Он не читает и не изменяет таблицы экзаменов монолита. Core отдаёт проверенные активные ссылки через `POST /internal/core/exam-references`; прямых записей в core/auth нет. Автоматический перенос старых экзаменов в эту реализацию не входит. Локальный Go BFF и React UI подключены через публичный контракт; перечень и проверка описаны в [интеграции BFF](../bff/exams-integration.md).

## Поведение

- Устный классический экзамен: 1–6 равноправных экзаменаторов, готовность каждого, запуск внутри окна, случайный выбор по оставшимся квотам частей. После старта действует неизменяемый снимок банка и правил; состав закреплён в назначении. Ученик не отправляет текстовый ответ.
- Голоса только 0/0.5/1. Требуется единогласие. При расхождении открывается новый раунд того же вопроса. До закрытия раунда экзаменатор видит свой голос и счётчик остальных. Обычный следующий вопрос открывается явной командой; завершение и дополнительный вопрос автоматические.
- Замена только до любого голоса, в той же части и в пределах общей льготы ученика. Заменённый вопрос исключается навсегда. Дополнительные вопросы используют циклы банка без непосредственного повтора.
- Баллы рассчитываются в целых половинах, без float-погрешности. Порогов ровно шесть, оценки 0–5. Дополнительный вопрос разрешает только округление, не добавляет обычные баллы.
- Одна пересдача после завершённой первой попытки, с изменённым набором экзаменаторов; завершённая пересдача становится действующей даже при худшей оценке. Апелляция меняет только итоговую оценку и сохраняет историю.
- Физическое удаление истории требует свежего предпросмотра, подтверждения и поколения истории. Первое назначение и льгота сохраняются, повторные назначения и история попыток удаляются. Предпросмотр удаления всего экзамена считает связанные данные во всех подключённых подразделениях.
- Внешний результат хранит числовые баллы с точностью до двух знаков и отдельную оценку 0–5; автоматического перевода баллов в оценку нет. Внешние результаты не доступны через классические команды.
- XLSX: вопросы, назначения/льготы и внешние результаты; файл ≤10 MiB, распаковка ≤64 MiB, один непустой лист, ≤5000 строк и ≤32 колонок. Формулы, даты и bool не вычисляются и отмечаются ошибками строк. Предпросмотр принадлежит создавшему аккаунту и подразделению, живёт 72 часа. Правки требуют ревизию. Commit атомарный, исключённые строки пропускаются, существующие результаты/назначения не перезаписываются. Завершённый предпросмотр хранится семь дней. Назначение через JSON и его льгота редактируются отдельными командами; импорт применяет их атомарно.
- Подготовка использует живой банк. Прогресс и настройки разделены по экзамену, подразделению и аккаунту. Изменение вопроса/ответа делает старый SHA256-отпечаток устаревшим; отметка требует актуальный отпечаток. Пустую подготовку включить нельзя.

## API и конкурентные изменения

Контракт доступен по `GET /openapi.json` (OpenAPI 3.1). Публичные пути начинаются с `/v1/exams`, JWT передаётся как Bearer. Основные ресурсы: `config`, `parts`, `questions`, `commissions`, `assignments`, `privileges`, `readiness`, `attempts`, `results`, `outside-results`, `imports`, `training`. Каталог фильтруется по `scope=division|bank|organization`, типу, направлению и названию. Изменения общего экзамена: `metadata`, `bank`, `direction`, `connections`, `copy`.

Любая запись, включая готовность, голоса, импорт и подготовку, требует UUID `Idempotency-Key`. Ключ связан с организацией, аккаунтом, методом, путём, query, телом и выбранным подразделением. Повтор того же запроса возвращает прежний результат; иное использование ключа — 409. Текущие права и принадлежность к комиссии повторно проверяются перед возвратом сохранённого результата. Все изменения и квитанция фиксируются одной SQL-транзакцией.

Ответ квитанции хранится семь дней. Затем запрос с тем же ключом возвращает `410 idempotency_expired`, включая период до фоновой очистки. Очистка оставляет компактную запись ключа и хеша навсегда, поэтому истечение срока не превращает повтор команды в новую запись. Импорт проверяет доступность и срок собственной сессии перед повтором квитанции; после срока — `410 import_expired`, после удаления payload очисткой — `404 not_found`. При неизвестном исходе commit повторяют исходный ключ; после истечения сессии автоматическое повторное применение с новым ключом недопустимо.

Каталог и результаты принимают `date_from`/`date_to` (также `from_date`/`to_date`), включительно по календарю UTC+03. Конфликтующие, некорректные и обратные границы отклоняются. Дата классического экзамена — текущий старт выбранного подразделения, внешнего — его `date`; исторический снимок окна попытки остаётся отдельным полем. Каталог фильтруется и сортируется до пагинации: `date_desc` по умолчанию, `date_asc`, `created_desc`, `direction_asc` по имени направления из Core с именем экзамена как fallback и ID для одинаковых имён. Несвязанный экзамен банка не получает чужую дату. В summary доступны выбранные дата, окно и `training_enabled`; служебные owner/origin/connection IDs и in_bank выдаются только административным ролям.

POST/GET/PUT предпросмотра возвращают максимум 200 строк (по умолчанию 100), `total`, `limit`, `offset`, `has_more`, `revision`, хеш исходного файла и сводку всех ошибок. При чтении нескольких страниц передают `expected_revision`, чтобы изменение превью не смешало версии. XLSX-шаблон создаёт владелец формата: `GET /v1/exams/{exam}/imports/{kind}/template`, с проверкой тех же прав и области организации/подразделения.

Фоновый импорт через Uploads использует [контракт Auth v1 revision 2](../auth/docs/import-operation-grants-v1.md) и [проверки владельца Exams](docs/background-import-contract.md). В исходниках реализованы отдельное удостоверение Exams для Auth, текущие права исходного пользователя, привязка команды к org/div/job/exam/session и проверка полного хеша предпросмотра под блокировкой. Предпросмотр дополнительно публикует `exam_revision` и отсортированные `connected_division_ids`; для вопросов нужны права изменения во всех текущих подразделениях. Все фоновые стадии несут исходный UUID команды, даже чтение. Публичный bearer-путь сохранён. Без пары отдельных `AUTH_OPERATIONS_EXAMS_KEY` и `EXAMS_OPERATIONS_DELIVERY_KEY` фоновые вызовы выключены; частичная или совпадающая конфигурация ключей не допускается. Развёртывание и совместная проверка UI → Uploads → Rabbit → Exams выполняются отдельно после готовности Auth, эти исходники сами по себе не означают включение фонового применения.

`GET /v1/exams/{exam}/imports/{kind}/{session}/receipts/{receipt}` только читает квитанцию исходной команды с текущими правами создателя. Метод не вызывает commit и не требует живого редактируемого предпросмотра. Он не принимает query или тело, сохраняет семидневный срок квитанции и запрет восстановления истёкшего ключа. Недоступная квитанция означает неизвестный исход, а не отсутствие изменений.

Объектные правки требуют `expected_revision`, переходы — `expected_state_version`, апелляция — `expected_result_version`, ensure/пересдача/удаление истории — `expected_history_generation`. Ревизии возвращаются в DTO; `division_revision` используется для переключения подготовки. Удаление экзамена/истории также требует `X-Exam-Confirmation` из соответствующего `delete-preview`. Удалённый экзамен допускает повтор квитанции удаления только при сохранённых правах редактирования.

## Рейтинг и события

`GET /internal/exams/rating-snapshot` требует `X-Service-Key`, организацию, до 100 подразделений, даты периода и необязательный `as_of`. Снимок читается в одной repeatable-read транзакции и возвращает каталог подходящих экзаменов, действующие оценки, вектор ревизий подразделений и ближайший будущий старт. Классические экзамены включаются по московской дате старта и `start_at <= as_of`; внешние — по дате экзамена в периоде. Отсутствующий результат отличается от опубликованного нуля. Отдельный сервис ratings соединяет каталог с участниками core, учитывает отсутствующие результаты нулём и использует число экзаменов как знаменатель. Для этого требуется его конфигурация `RATINGS_EXAMS_MODE=required` и действующий exams URL; dev-режим `dev_empty` подставляет пустой компонент и не подтверждает рейтинг с экзаменами. Сервис экзаменов не рассчитывает общий рейтинг и не подключён к существующему calculate автоматически.

В той же транзакции, что и изменение входа рейтинга, обновляется ревизия подразделения и создаётся `exams.source.changed` в outbox. Worker публикует устойчивое сообщение в topic exchange `cpm.events` с обязательной маршрутизацией и publisher confirm. Без получателя или при потере соединения событие остаётся pending. Доставка at least once: получатель должен устранять дубли по `message_id`, сравнивать `source_revision` и получать новый согласованный снимок. Сервис не создаёт очередь ratings. Пустой `RABBITMQ_URL` отключает доставку, но сохраняет outbox; в dev-конфигурации брокер задан.

В snapshot `exam_revision` и `division_revision` — отдельные смысловые версии входа рейтинга. Незавершённые голоса, комиссия, подготовка и апелляция к старой попытке не меняют действующий рейтинг. Завершение или действующая апелляция меняют только своё подразделение; название (`exam_name`) и направление меняют все связи. Техническая версия агрегата применяется к CAS и остаётся в событии `exam_revision`; получатель использует монотонный `source_revision` по организации и подразделению. Истечение `as_of` ограничивает включение по старту, сохраняя исходную семантику оценки из согласованного снимка, без восстановления исторического состояния на эту секунду.

## Хранение и ограничения

Сортировка `direction_asc` сравнивает scoped названия без учёта регистра и затем ID экзамена. Она не воспроизводит полностью языковые правила MySQL collation для произвольных акцентов; это не влияет на оценку, период или ревизию рейтинга.

Экзамен хранится как JSON-агрегат с SQL-блокировкой строки при записи. Неизменяемые версии определений дедуплицируются: одинаковые снимки банка и правил хранятся один раз, попытки ссылаются на них. Операционные состояния подразделений остаются независимыми. Такой подход обеспечивает атомарность переходов и импортов; изменения одного общего экзамена сериализуются. Это первая реализация, а не подтверждение SLA на 450 одновременно проводимых экзаменов. Для такого SLA требуется отдельный нагрузочный прогон с реальными размерами банка и комиссии. Агрегат ограничен 40 MiB, живой банк — 16 MiB и 5000 вопросов. Несколько разных исторических банков максимального размера могут исчерпать предел агрегата: следующая запись вернёт 422 без частичного применения. Неиспользуемые снимки убираются при сохранении после удаления соответствующей истории. Каталог пока читает агрегаты организации перед фильтрацией; большой архив потребует отдельной проекции каталога и выделения попыток и версий определений в строки.

## Локальный запуск и проверки

Требуются уже подготовленные Core :8003, auth :8002, MySQL :13306/cpm_dev и RabbitMQ loopback/cpm_dev. Скрипты принимают только локальную dev-базу. Настройки берутся из игнорируемого `dev/.env`, генерируемые `dev/local/exams.env` и `exams-compose.env` приватные. Миграции применяются только к таблицам Exams и повторяемы.

```sh
./dev/exams prepare
./dev/exams up
./dev/exams test
./dev/exams status
./dev/exams down
```

`up` собирает и запускает только контейнер Exams :8010 с `--no-deps`, используя действующий Core :8003. `down` удаляет только этот контейнер. `dev/compose.exams.yaml` задаёт Docker profile `exams`, непривилегированного пользователя, read-only filesystem и healthcheck. `offline-build`/`offline-up` используют локальный Go и отдельный тег уже закешированного Linux runtime, без загрузки из registry и изменений контейнера Core. Legacy `local_run.py` остаётся для отдельной отладки; не запускайте его одновременно с Docker на том же порту.

Проверки включают Go unit/race/vet, сравнение чистых правил с исходным Python, фазовые сценарии, приватность, CAS, копирование, импорты, отпечатки, границы HTTP и живой HTTP-прогон с синтетическими данными. HTTP-скрипт очищает свои фикстуры и сохраняет приватный отчёт `dev/local/exams-http-report.json`. Нагрузочная часть из 450 чтений с 32 workers — smoke, не имитация 450 одновременных устных сессий. Реальная проверка outbox запускается отдельно с `CPM_EXAMS_OUTBOX_INTEGRATION=1`; она использует временные SQL-таблицы и собственный AMQP exchange/queue. Без этого флага стандартные Go-тесты не зависят от работающих баз и брокера.

`CPM_EXAMS_OPERATIONS_INTEGRATION=1 go test -race ./...` отдельно проверяет три фоновых типа на настоящих SQL-транзакциях и квитанциях во временных таблицах одной локальной MySQL-сессии. Auth и Core в этом тесте заменены контролируемыми заглушками; это не полный прогон очереди и интерфейса. Приватный отчёт адресных проверок: `dev/local/exams-operations-integration-report.json`.

Дополнительный `services/bff/scripts/exams_http_test.py` выполняет сценарии только через public API и cookie BFF, сохраняет свежие DEV фикстуры для браузера и не вызывает SQL cleanup. `services/bff/scripts/exams_rabbit_check.py` проверяет реальную доставку в существующем DevRabbit через свою временную очередь с точной привязкой `cpm.events` / `exams.source.changed`, удаляет только эту очередь и не приостанавливает контейнеры. Отчёты находятся в `dev/local/bff-exams-*-report.json`.
