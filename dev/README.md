# Локальный dev-контур CPM

Контур на Mac для разработки сервисов. Docker Desktop установлен в `/Applications/Docker.app`; контейнеры видны в его разделе Containers → `cpm-dev`. В контур подключены MySQL, MongoDB, auth, core, tests, calculate и RabbitMQ. Дополнительный Compose-файл включает homework и file-work-service.

## Подключение

| БД | Адрес с Mac | База | Пользователь |
|---|---|---|---|
| MySQL 8.0.46 | `127.0.0.1:13306` | `cpm_dev` | `cpm_dev` |
| MongoDB 8.0.17 | `127.0.0.1:27018` | `cpm_dev` | `cpm_dev`, authSource=`cpm_dev` |

Пароли находятся в `.env`, готовая строка MongoDB — в `local/backend.env`. Эти файлы исключены из Git. Порты опубликованы только на loopback; MySQL и MongoDB используют разные пароли и отдельные Docker-тома. Каждому контейнеру задан предел памяти 1,5 ГиБ. Это локальные настройки разработки, а не оценка ресурсов production на 450 учеников.

## Ежедневная работа

Из корня проекта `cpm`:

```sh
./dev/dev up
./dev/dev auth-up
./dev/dev tests-up
./dev/dev status
./dev/dev logs
./dev/dev stop
```

Docker Desktop должен быть запущен. `up` запускает БД, `auth-up` собирает и запускает авторизацию с dev MySQL. `tests-up` готовит новые коллекции и запускает auth/core/tests/calculate/RabbitMQ вместе с БД. `calculate-up` выполняет тот же запуск: worker требует внутреннего API tests для записи результатов. `stop` останавливает весь контур и сохраняет содержимое БД и очередей. Не удаляйте тома в Docker Desktop, если нужны накопленные dev-данные. Скрипт находит Docker внутри приложения, даже если команда `docker` пока не добавлена в PATH.

Auth доступен по `http://127.0.0.1:8002`. Go установлен в пользовательский каталог и доступен командой `go` в новом терминале. Настройки для запуска auth на Mac — `local/auth.env`; в контейнере используются имена Docker-сети. Закрытый ключ находится в `local/auth-private.pem` и отдельном Docker-томе. Инструкция и HTTP-контракт: `../services/auth/README.md`.

## RabbitMQ и calculate

В `compose.yaml` добавлен RabbitMQ с management UI, профиль `rabbit`. Команды `up`, `auth-up` и `core-up` его не включают. `tests-up` и `calculate-up` запускают брокер. Сервисы объявляют durable topic exchange `cpm.events`, quorum queue `calculate.events.v1` с маршрутами `tests.grade.requested.v1` и `tests.content.changed.v1`, а также очередь отклонённых сообщений `calculate.events.dead.v1` через exchange `cpm.events.dead`.

Общие настройки находятся в `dev/.env`: `RABBITMQ_IMAGE`, `RABBITMQ_HOST`, `RABBITMQ_PORT`, `RABBITMQ_MANAGEMENT_PORT`, `RABBITMQ_USER`, `RABBITMQ_PASSWORD`, `RABBITMQ_VHOST`, `RABBITMQ_ERLANG_COOKIE`. Там же формируются готовые адреса подключения:

| Переменная | Для чего |
|---|---|
| `RABBITMQ_URL` | Go-сервис на Mac → `127.0.0.1:5672`, vhost `cpm_dev` |
| `RABBITMQ_DOCKER_URL` | Go-сервис в сети этого Compose → `rabbitmq:5672`, vhost `cpm_dev` |
| `RABBITMQ_MANAGEMENT_URL` | Интерфейс управления → `http://127.0.0.1:15672` после запуска |

AMQP-адреса содержат пароль: не публикуйте их в логах и документах. Сгенерированный `local/rabbitmq.env` — копия настроек для локального запуска сервисов, а не отдельный источник параметров. Оба файла имеют права `0600` и исключены из Git. В Compose tests и calculate получают `RABBITMQ_DOCKER_URL` в своей переменной `RABBITMQ_URL`; Mac-конфигурации получают loopback-адрес.

Обновить настройки без Docker, БД и сетевых запросов:

```sh
./dev/dev rabbit-prepare
```

Команда создаёт случайные пароль и Erlang cookie при отсутствии настоящих значений, сохраняет существующие секреты и не меняет настройки других сервисов. После ручного изменения RabbitMQ-параметров в общем `.env` выполните её снова для обновления адресов и копии.

Отдельный запуск брокера:

```sh
./dev/dev rabbit-up
```

Это явный запуск только RabbitMQ; MySQL, MongoDB, auth и core от него не зависят. Docker Desktop должен уже работать. Интерфейс управления использует те же локальные логин и пароль из `.env`. AMQP и management публикуются только на `127.0.0.1`. Объявлен постоянный том `rabbitmq-data`, стабильные hostname и имя узла; `stop` сохраняет данные брокера. Параметры default user/vhost применяются при первой инициализации пустого тома: последующее редактирование `.env` само по себе не меняет пароль пользователя в существующем брокере.

Выбран точный тег `rabbitmq:4.3.6-management` из [официального каталога Docker-образа](https://github.com/docker-library/docs/blob/master/rabbitmq/README.md). Контейнеру задан предел 768 МиБ, порог памяти RabbitMQ — 512 МиБ в `rabbitmq/rabbitmq.conf`, порог свободного диска — 2 ГБ. Абсолютный порог памяти выбран по [документации RabbitMQ для контейнеров](https://www.rabbitmq.com/docs/memory). Healthcheck выполняется от пользователя `rabbitmq`, чтобы читать его Erlang cookie при снятых capabilities. Эти значения относятся к локальному dev-контуру и потребуют проверки при реальной нагрузке.

Calculate доступен на `http://127.0.0.1:8005`. Worker сохраняет сообщения в `calculate_inbox_v1`, подтверждает доставку после записи, затем асинхронно проверяет официальные сдачи и обрабатывает пересчёты после редактирования теста. Результат записывает tests через защищённый внутренний API с проверкой ревизии и хеша входа. Организация управляет пересчётами через `GET/PUT /v1/core/organization/test-settings`; по умолчанию пересчёт включён, менять настройку может администратор организации. Отдельные синхронные методы сохраняют немедленную обратную связь в тренировке. У tests при недоступном брокере сдача остаётся принятой, событие хранится в документе сдачи и отправляется после восстановления соединения. Готовность tests не зависит от текущей доступности RabbitMQ; готовность calculate включает активного consumer.

## Что скопировано

Снимок структуры получен 6 октября 2026 года: **79 таблиц MySQL** с колонками, индексами и внешними ключами; **9 коллекций MongoDB** с настройками и индексами, включая unique и partial. Экспорт выполнялся запросами метаданных, без чтения пользовательских строк и документов и без записи в production.

Источник: MySQL `8.0.22-13`, MongoDB `8.0.17-6`. Локально используются официальные ARM64-образы с той же основной версией 8.0; патч MySQL и сборки поставщика отличаются. Теги и скачанные digest записаны в `images.lock.txt`. MongoDB работает как одиночный сервер без replica set; распределённые транзакции этим контуром не проверяются.

Четыре production-процедуры (`pivot_exams`, `pivot_exams12345`, `pivot_homework`, `pivot_tests`) не импортированы: текущий объём — таблицы и коллекции. Production-триггеров и событий в метаданных нет. Если дальнейшая разработка потребует процедур, их перенос надо выполнить отдельно. Коллекция `migration_backup_tests_offline_20260717` создана пустой, как и остальные коллекции без тестовых сценариев.

Снимки лежат в `schema/mysql.sql`, `schema/mysql.json`, `schema/mongo.json` и исключены из Git. Они не содержат пользовательских записей, но относятся к внутренней структуре проекта.

## Конфигурации приложений

Подготовлены `local/backend.env`, `local/homework.env` и `local/frontend.env`. Само наличие файлов не переключает приложения на dev: их нужно явно загрузить **до импорта приложения**. В существующем backend есть production-значения по умолчанию; не запускайте его без выбранной dev-конфигурации.

Эти адреса подходят для приложений, запускаемых на Mac. При переносе приложений в Compose будут нужны имена `mysql:3306` и `mongo:27017` внутри сети, а не `127.0.0.1`.

## Воспроизведение и проверка

На этом Mac Python-окружение уже подготовлено. Для нового окружения нужен Python 3.12:

```sh
python3.12 -m venv dev/.venv
dev/.venv/bin/pip install -r dev/requirements.lock.txt
dev/.venv/bin/python dev/scripts/init_env.py
./dev/dev up
dev/.venv/bin/python dev/scripts/bootstrap.py
dev/.venv/bin/python dev/scripts/verify.py
```

Перед bootstrap нужны локальные снимки в `schema/`. Их можно получить отдельно явным вызовом экспорта с файлом доступа к источнику:

```sh
dev/.venv/bin/python dev/scripts/export_structure.py --source-env /path/to/source-access.env
```

Обычный запуск контура к production не обращается. Bootstrap создаёт недостающие таблицы/коллекции и начальные данные, не удаляет существующие данные и не выполняет миграции изменившихся таблиц. Повторный seed пропускается по маркеру в `local/`. После ручного удаления томов маркеры могут не соответствовать БД — восстановление следует делать осознанно, а не удалять только один компонент.

`verify.py` проверяет полное DDL исходных 79 таблиц (кроме текущих счётчиков AUTO_INCREMENT и эквивалентного отображения кодировок между патчами MySQL), допускает только перечисленные новые таблицы, проверяет настройки и индексы коллекций, сохранность исходных учеников и хешей 20 начальных аккаунтов. Результат сохраняется в `local/verification.json`. До создания нового auth также проверен вход во все 20 аккаунтов через текущую функцию `auth` backend, отказ при неверном пароле и соответствие хеша версии Mongo-теста текущему коду.

Подготовка данных нового auth и HTTP-проверка:

```sh
dev/.venv/bin/python services/auth/scripts/dev_setup.py
./dev/dev auth-up
dev/.venv/bin/python services/auth/scripts/http_test.py
```

Перед первым `auth-up` нужно сгенерировать ключ, как описано в инструкции auth. Его HTTP-отчёт — `local/auth-http-report.json`. Все тесты используют исключительно локальную БД и вымышленные аккаунты.

Это проверка исходного seed: после собственной работы с данными ожидаемые количества могут измениться.

Установка Docker выполнена из [официального дистрибутива для Mac](https://docs.docker.com/desktop/setup/install/mac-install/). Исходный установщик сохранён в `~/Downloads/Docker-cpm-arm64.dmg`.

Сервис — `services/core`. Telegram отсутствует, кроме поля `tg_name`; тесты, карточки, экзамены, ДЗ и рейтинг вынесены за его границы.

Локальный адрес `http://127.0.0.1:8003`, контракт `/openapi.json`. Каждый бизнес-метод проверяет токен через auth и доступ к организации, подразделению и объекту. [Состав, AS IS, DTO и ограничения](../services/core/README.md). Новые таблицы разрешены в `schema/extensions.json`; исходные структуры сохраняются.

## Homework и file-work-service

Homework хранит задания, типы каждого подразделения, результаты, файловый workflow и аудит в девяти новых таблицах `hw_*`. File-work-service получает команды из RabbitMQ, скачивает PDF из S3, проверяет и сжимает его с помощью qpdf/Ghostscript, возвращает результат сообщением. Бизнес-записи сохраняет homework. PDF для рабочего развёртывания остаются во внешнем S3.

Для интеграционных тестов есть отдельный локальный S3 fixture с bucket `cpm-homework-test`. Он включается явно:

```sh
./dev/dev homework-prepare --test-s3
./dev/dev homework-up
./dev/dev status
```

`homework-prepare` обновляет приватные конфигурации, сохраняет текущие секреты RabbitMQ и не запускает Docker, БД или сеть. `homework-up` готовит аддитивную схему только в `127.0.0.1:13306/cpm_dev`, собирает core/homework/file-work-service, запускает RabbitMQ и зависимости. В режиме fixture он также собирает S3, создаёт только тестовый bucket и сохраняет его отдельный том. Исходные 79 таблиц не меняют структуру; задания из старой системы не переносятся. `stop`, `status` и `logs` автоматически учитывают дополнительный Compose-файл при наличии сгенерированной конфигурации.

| Компонент | Локальный адрес |
|---|---|
| Homework | `http://127.0.0.1:8006` |
| File-work-service | `http://127.0.0.1:8007` |
| Тестовый S3 | `http://127.0.0.1:19000` |
| Консоль тестового S3 | `http://127.0.0.1:19001` |

Файлы `local/homework-go.env`, `local/file-work.env`, `local/homework-compose.env` исключены из Git и имеют права `0600`. Контейнеры используют `s3-test:9000`, браузерные подписанные адреса — `127.0.0.1:19000`. Тестовый S3 собирается из [официального MinIO RELEASE.2025-10-15T17-29-55Z](https://github.com/minio/minio/releases/tag/RELEASE.2025-10-15T17-29-55Z), с фиксированным commit `9e49d5e7a648f00e26f2246f4dc28e6b07f8c84a`; первая сборка загружает его зависимости Go. Worker обрабатывает один PDF одновременно; ему выделены 1 ГиБ памяти и 512 МиБ временного диска.

Для отдельного внешнего **dev** S3 задайте в `dev/.env` переменные `HOMEWORK_S3_ENDPOINT_URL`, `HOMEWORK_S3_PUBLIC_ENDPOINT_URL`, `HOMEWORK_S3_BUCKET`, `HOMEWORK_S3_REGION`, `HOMEWORK_S3_ACCESS_KEY_ID`, `HOMEWORK_S3_SECRET_ACCESS_KEY`. Если адрес контейнеров отличается, задайте `HOMEWORK_S3_DOCKER_ENDPOINT_URL`. Затем выполните `./dev/dev homework-prepare` без `--test-s3`. Пока эти значения отсутствуют, генерируется локальный неработающий placeholder. Production-ключи и bucket для разработки не используются.

Настройки обработки хранятся в существующей `application_settings` под ключом `homework.{division_id}.limits`. Начальные пределы: 10 MiB до и после сжатия, 35 страниц, 120 dpi, JPEG quality 75. Параметры сохраняются в снимке задания; изменение настроек применяется к следующим загрузкам. При повторной подготовке существующие значения сохраняются. [Модель и API](../services/homework/README.md).

## Tests на Go: каталог, вопросы и сдачи

```sh
./dev/dev tests-up
dev/.venv/bin/python services/tests/scripts/http_test.py
dev/.venv/bin/python services/tests/scripts/workflow_test.py
dev/.venv/bin/python services/tests/scripts/grading_test.py
dev/.venv/bin/python services/tests/scripts/acceptance_race_test.py
dev/.venv/bin/python services/calculate/scripts/http_test.py
dev/.venv/bin/python dev/scripts/verify.py
```

Команда сначала поднимает локальные MySQL/Mongo, переводит направления core на уровень организации (ID сохраняются), готовит новые коллекции и настройки RabbitMQ, затем собирает и запускает весь контур. Сервис tests: `http://127.0.0.1:8004`, контракт `/openapi.json`, [модель и API](../services/tests/README.md). Поддерживаются банк, привязка общего теста, независимая физическая копия с вопросами, три типа вопросов, версии, история изменений, черновики, случайный порядок, офлайн-повторы и асинхронный приём сдачи. Выбранное подразделение фильтрует каталог до подсчёта количества и пагинации; сдача хранит подразделение начала.

Коллекции tests/calculate: `tests_catalog_v1`, `tests_content_versions_v1`, `tests_drafts_v1`, `tests_attempts_v1`, `tests_calculation_jobs_v1`, `calculate_inbox_v1`; они перечислены в `schema/mongo-extensions.json`. Настройка организации хранится в новой таблице `core_organization_test_settings`. Исходные девять коллекций сохраняют настройки и индексы. Конфигурации `local/tests.env`, `local/calculate.env` и отчёты `local/tests-http-report.json`, `local/tests-workflow-report.json`, `local/tests-grading-report.json` исключены из Git. Workflow и grading создают тесты через API и очищают свои временные записи. Проверки временно останавливают RabbitMQ и calculate, проверяют приём сдачи, доставку и результат после запуска; `--skip-faults` оставляет сценарии без остановки контейнеров. Для проверки границ времени workflow сдвигает даты только собственных попыток, заранее созданных через API, и удаляет их после проверки. Grading сравнивает результаты с неизменённым Python-алгоритмом старого сервиса и проверяет непосредственно MongoDB: исходные ответы, идентификаторы, подразделение, веса, результаты вопросов и перезапись той же сдачи.

`workflow_test.py --demo` выполняет отдельный короткий сценарий: создаёт один тест с тремя типами вопросов, подключает его к подразделениям 1001 и 1002, создаёт независимую копию в 1002 и одну сдачу, дожидается её рассчитанного результата. Эти два теста и одно направление сохраняются для просмотра; временные сотрудники и роли не создаются. Безопасные ID находятся в `local/tests-demo.json`, отчёт — в `local/tests-demo-report.json`; все токены завершаются через auth logout.

## Cards на Go

Организационные темы/карточки и единый прогресс доступны на `http://127.0.0.1:8008`. Отдельный профиль: `compose.cards.yaml`, команды `./dev/cards prepare`, `./dev/cards integration-up`, затем `dev/.venv/bin/python services/cards/scripts/seed.py` и `./dev/cards test`. `integration-up` адресно собирает core/tests/cards с `--no-deps` для новых внутренних API; существующие auth/MySQL/Mongo должны уже работать. RabbitMQ и остальные сервисы этой командой не запускаются и не останавливаются. Синтетические credentials — только `local/cards-fixtures.json`, отчёт без секретов — `local/cards-http-report.json`.
